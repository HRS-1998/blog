# 2 TypeScript

对标 P6/P7 的 TypeScript 面试考察：类型系统本质、泛型与类型体操、条件类型与 infer、编译原理与 tsconfig 工程化、性能优化与渐进式迁移。每题给出核心答案、知识点拆解与 P7 视角的加分项。

## Q：TypeScript 是结构性类型语言，这意味着什么？与名义类型有何区别？

**核心答案**：TypeScript 的类型兼容性由"形状"决定而不是由"名字"决定——只要两个类型的成员结构能互相匹配，它们就兼容，不需要显式继承或实现同一个接口。名义类型系统（Java、C#、Rust）则要求变量必须通过显式声明的类型名或继承链来判定归属。结构化类型本质上是"编译期的鸭子类型"：编译器做结构比对，但不会阻止两个毫无关系的类型因为碰巧同构而互相赋值。需要名义语义时，要手动构造品牌类型（branded type）。

**知识点解析**：

- 结构化赋值：结构相同即可互赋，无需任何显式关联。

```ts
interface Point { x: number; y: number }
interface Vec2 { x: number; y: number }

const p: Point = { x: 1, y: 2 };
const v: Vec2 = p; // OK：纯结构匹配
```

- 名义类型下 Point 和 Vec2 即使结构完全相同也不能互赋；结构化类型没有"身份"概念，只有"关系"。
- 超额属性检查（excess property check）只针对"新鲜"对象字面量，经过一个中间变量即可绕过。

```ts
interface Options { timeout: number }

const o1: Options = { timeout: 1, extra: true }; // 报错：多余属性
const tmp = { timeout: 1, extra: true };
const o2: Options = tmp; // OK：tmp 不是新鲜字面量
```

- 品牌类型（branded type）模拟名义类型：交叉一个不存在的标记属性，让结构"不再相同"。

```ts
type UserId = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };

function getUser(id: UserId): void {}

const uid = 'u_1' as UserId;
getUser(uid);   // OK
getUser('u_1'); // 报错：纯 string 不能当 UserId
```

- 弱类型检测（weak type detection）：只有可选属性的类型（weak type），赋值对象必须至少有一个重叠属性，防止完全无关的对象误传。

**加分项（P7 视角）**：

- 编译器层面：结构兼容判定由 checker 的 relation（isTypeRelatedTo）机制完成，比较结果有缓存与 "indeterminate" 状态以避免指数级重复比较；深度嵌套的泛型结构会显著放大比较成本，这是大型项目类型检查慢的根因之一。
- 用 `declare const brand: unique symbol` 配合交叉类型可以做出更强的名义化 brand，比字符串字面量更难伪造，且 TS 4.6+ 的控制流分析能识别 in 操作符对品牌属性的判别。
- 结构化类型的跨包隐患：两个无关模块各自定义的相同结构会意外兼容（比如 userId 和 orderId 都是 string），导致语义性 bug 传错参数。金融、权限等强业务语义场景建议在公共 API 层统一使用 branded type——这是可以直接落地讲的团队经验。

## Q：interface 和 type 有哪些差异点？分别什么时候用？

**核心答案**：两者都能描述对象形状，但 interface 只能描述对象/函数类型且支持声明合并，type 是类型别名，能表达联合、元组、映射类型、条件类型等全部类型运算能力。社区共识是：库的公共 API、希望被使用方扩展的类型用 interface；内部类型、需要类型体操的场景用 type。此外 interface 在错误提示和编译性能上更好——它生成单一扁平的对象类型声明，编译器可以直接缓存比较。

**知识点解析**：

- 差异一：声明合并（declaration merging）只有 interface 支持，type 重复声明直接报错。

```ts
interface Window { __APP__: string }
// 全局 Window 被合并出新属性，type 无法做到

interface Logger { log(m: string): void }
interface Logger { warn(m: string): void } // 合并成两个方法的接口
```

- 差异二：继承方式不同。interface 用 extends（可多继承、可 extends 一个对象类型的 type），type 用交叉 `&`。冲突处理不同：extends 遇到同名属性类型不兼容直接报错；`&` 会静默生成 never，把错误推迟到使用处。

```ts
interface A { x: number }
interface B extends A { x: string } // 报错：类型不兼容

type C = { x: number } & { x: string };
const c: C = { x: 1 as never }; // 属性 x 是 number & string（即 never），错误被推迟暴露
```

- 差异三：type 可以定义联合、元组、原始类型别名、字面量类型，interface 只能描述对象/函数形状。

```ts
type ID = string | number;
type Pair = [string, number];
type Callback = (e: string) => void;
type Method = 'GET' | 'POST';
```

- 差异四：映射类型、条件类型、infer 只能出现在 type 里（interface 的成员列表是静态的，不能由另一个类型计算得出）。

```ts
type Partial2<T> = { [K in keyof T]?: T[K] };          // 映射类型
type Await2<T> = T extends Promise<infer V> ? V : T;   // 条件类型 + infer
```

- 差异五：性能与错误提示。官方 Wiki 明确说明 interface 创建"单一扁平的对象类型 map"，比交叉类型的递归展开更快，类型提示更友好（显示接口名而非匿名展开）。
- 差异六：作用域扩展方式。interface 可以被 `declare module`、`declare global` 合并扩展（第三方库的模块扩充能力都依赖它），type 别名无法参与合并。

**加分项（P7 视角）**：

- interface extends type 的限制：只能 extends 静态已知的对象类型，不能 extends 联合类型或条件类型结果；而 `&` 交叉可以组合任何类型——所以工具类型库全部基于 type。
- 深度交叉的性能陷阱：`(A & B) & (C & D) & ...` 会构建深层交叉树，悬垂显示和缓存都更差；Vue/Vite 等大型代码库在性能敏感的类型上刻意改用 interface + extends（Vite 源码和 TS 官方性能文档都有案例）。
- 团队规范建议写进 lint/code review：对外 .d.ts 的 API 类型用 interface 留出扩展能力，内部一律 type；并说明"type 重复声明报错"本身也是一种防冲突保护。

## Q：泛型的约束 extends、默认值怎么用？手写一个类型安全的 TypedEventEmitter。

**核心答案**：泛型让类型成为可传参的函数——`<T extends U>` 限定 T 必须满足 U 的结构（约束后才能安全访问其成员），`<T = Default>` 提供默认类型实参，泛型类让整个类的成员共享同一类型参数。TypedEventEmitter 的核心思路：用 `Record<keyof Events, unknown[]>` 把"事件名到参数元组的映射"作为泛型约束，再配合 `keyof Events` 索引约束，让 on/emit 的参数在编译期逐一对应。这是 Vue defineEmits 同款类型方案。

**知识点解析**：

- extends 约束：约束之后才能使用约束类型的属性，`K extends keyof T` 是最常用的联动约束。

```ts
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
```

- 默认类型参数：让调用方少写模板参数。

```ts
interface ApiResponse<T = unknown, E = Error> {
  code: number;
  data: T;
  error?: E;
}
```

- 泛型类：静态成员不能引用类的类型参数（静态成员属于类本身而非实例）。
- TypedEventEmitter 完整实现：

```ts
type Listener<Args extends unknown[]> = (...args: Args) => void;

class TypedEventEmitter<Events extends Record<keyof Events, unknown[]>> {
  private listeners = new Map<keyof Events, Set<Listener<never[]>>>();

  on<K extends keyof Events>(event: K, listener: Listener<Events[K]>): () => void {
    const set = this.listeners.get(event) ?? new Set<Listener<never[]>>();
    set.add(listener); // 见下方“逆变”解释：never[] 让任何监听器都兼容
    this.listeners.set(event, set);
    return () => this.off(event, listener);
  }

  off<K extends keyof Events>(event: K, listener: Listener<Events[K]>): void {
    this.listeners.get(event)?.delete(listener);
  }

  once<K extends keyof Events>(event: K, listener: Listener<Events[K]>): () => void {
    const wrapped = ((...args: Events[K]) => {
      this.off(event, wrapped);
      listener(...args);
    }) as Listener<Events[K]>;
    return this.on(event, wrapped);
  }

  emit<K extends keyof Events>(event: K, ...args: Events[K]): void {
    this.listeners.get(event)?.forEach((fn) => {
      (fn as Listener<Events[K]>)(...args);
    });
  }
}

// 使用：参数个数、类型、事件名全部编译期校验
interface Events {
  change: [newValue: string, oldValue: string];
  error: [err: Error];
  ready: [];
}

const bus = new TypedEventEmitter<Events>();
bus.on('change', (nv, ov) => console.log(nv.toUpperCase(), ov));
bus.emit('change', 'a', 'b');   // OK
bus.emit('change', 'a');        // 报错：缺少参数
bus.on('unknown', () => {});    // 报错：事件名不存在
```

- 推断过程逐行解释：
  - `Events extends Record<keyof Events, unknown[]>` 是自引用约束，要求 Events 的每个值都是"参数元组"，比 `Record<string, any>` 强得多。
  - `on<K extends keyof Events>` 把 K 限定为具体事件名，从而 `Listener<Events[K]>` 拿到该事件的精确参数元组。
  - 私有 Map 的值类型是 `Listener<never[]>`：因为函数参数是逆变位置，`never` 是 bottom type、可赋值给一切类型，所以任何 `Listener<Events[K]>` 都能安全存进 `Set<Listener<never[]>>`，实现零 any 的存储。
  - emit 用 `...args: Events[K]` 接收展开参数，与监听器的元组一一对应。

**加分项（P7 视角）**：

- Vue 3 的 `defineEmits<{ (e: 'change', nv: string, ov: string): void }>` 与对象签名 `Record<event, tuple>` 两种写法正是同一套原理；能对照讲 emit 的类型推导说明对框架类型设计有理解。
- never 存储技巧的适用边界：它依赖逆变方向，只对"存进去不再改签名"的场景成立；若要对外暴露监听器列表，应返回 `readonly Listener<Events[K]>[]` 并在边界处收敛类型。
- 事件参数用命名元组 `[newValue: string, oldValue: string]`（TS 4.0+），IDE 悬停时能显示参数名，团队协作体验明显提升。

## Q：能手写 Partial / Required / Pick / Omit / Record / ReturnType 吗？原理是什么？

**核心答案**：这六个工具类型全部由"keyof + 索引访问 + 映射类型"三种机制组合而成。映射类型 `{ [K in U]: V }` 遍历键联合生成新对象类型；`?`/`-?`/`readonly` 是映射修饰符；Pick/Omit 用键集合过滤；Record 用键联合生成全新对象；ReturnType 用条件类型加 infer 从函数类型中抽取返回值。理解它们的实现就能自己组合出任意工具类型。

**知识点解析**：

- 六个工具类型的最小实现：

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K]; // 加上可选修饰符
};

type MyRequired<T> = {
  [K in keyof T]-?: T[K]; // -? 移除可选修饰符（含 undefined 的移除）
};

type MyPick<T, K extends keyof T> = {
  [P in K]: T[P]; // 只遍历 K 这个键子集
};

type MyOmit<T, K extends keyof T> = MyPick<T, Exclude<keyof T, K>>;

type MyRecord<K extends keyof any, V> = {
  [P in K]: V; // keyof any = string | number | symbol，即合法的键类型全集
};

type MyReturnType<T> = T extends (...args: never[]) => infer R ? R : never;
```

- keyof + 索引访问：`keyof T` 取键的联合，`T[K]` 按键取值类型，两者配合是所有对象变换的基础。
- 映射修饰符：`+?`（可省略加号）、`-?`、`readonly`、`-readonly`，MyRequired 的 `-?` 还会自动剔除 undefined。
- Omit 的第二种写法（TS 4.1 的 as 重映射），不要求 K 是 keyof T 的子集，语义更宽容：

```ts
type MyOmit2<T, K extends PropertyKey> = {
  [P in keyof T as P extends K ? never : P]: T[P]; // 命中被过滤的键映射为 never，从结果中剔除
};
```

- ReturnType 的推断原理：把 T 放进一个函数模式的"模板"里，`infer R` 声明"这个位置的类型请编译器帮我推断"，命中则 R 在真分支可用。
- Exclude 的实现本身就是分布式条件类型：`type Exclude<T, U> = T extends U ? never : T`，对联合成员逐一判断。

**加分项（P7 视角）**：

- 同构（homomorphic）映射类型：形如 `{ [K in keyof T]: ... }` 且保持 `T[K]` 原值的映射，会保留原类型的 optional/readonly 修饰符——Pick/Partial/Required 是同构的，Record 不是（它无源可保）。同构映射还能识别数组、元组并保持其结构，这是 Pick 可以作用于元组的原因。
- 官方 lib.es5.d.ts 里 ReturnType 的参数用 `(...args: any[]) => any`，any 是为了兼容各种函数（包括重载与 this 绑定），严格库（如 type-fest）用 never[] 版本 + `T extends Function` 约束，能讲出取舍差异。
- Omit 的官方实现是 `Pick<T, Exclude<keyof T, K>>`，其中 K 约束是 `string | number | symbol` 而不是 keyof T——这是有意为之（允许省略不存在的键），但也会吞掉拼写错误，团队内可用更严格的 MyOmit 版本防御。

## Q：手写 DeepReadonly / DeepPartial / Awaited / UnionToIntersection，讲讲推断过程。

**核心答案**：Deep 系列靠"映射类型 + 递归"：把每个属性值再递归地传入自身，直到不再是对象。Awaited 递归解包 Promise 的值类型。UnionToIntersection 是最反直觉的一个：先把联合分发为多个函数的联合，再利用"函数参数（逆变位置）的多个推断候选取交集"这条推断规则，把联合翻转成交集。这四个类型分别覆盖了递归映射、条件类型递归、逆变推断三大底层机制。

**知识点解析**：

- DeepReadonly / DeepPartial 及其边界处理：

```ts
type DeepReadonly<T> = {
  readonly [K in keyof T]: DeepReadonly<T[K]>;
};

// 更严谨的版本：函数与原始类型是递归的“叶子”，必须提前终止
type DeepReadonly2<T> = T extends (...args: never[]) => unknown
  ? T // 函数：保持原样，避免把参数也变 readonly
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly2<T[K]> }
    : T; // string/number 等原始类型直接返回

type DeepPartial<T> = {
  [K in keyof T]?: DeepPartial<T[K]>;
};
```

- 推断过程（以 `DeepReadonly2<{ a: { b: number }, fn: () => void }>` 为例）：
  - 整体命中 `T extends object` 分支，生成 `{ readonly a: ..., readonly fn: ... }`。
  - 属性 a 的值 `{ b: number }` 再传入 DeepReadonly2，再次命中 object 分支得到 `{ readonly b: number }`。
  - 属性 fn 的值是函数类型，命中第一个分支原样返回，递归终止——所以 `T extends object` 必须写在函数分支之后，函数也是 object，顺序错了就会把函数也映射掉。

- Awaited：递归解包嵌套 Promise。

```ts
type MyAwaited<T> = T extends Promise<infer V> ? MyAwaited<V> : T;

type A = MyAwaited<Promise<Promise<string>>>; // string：解包两次后不再是 Promise，走 false 分支返回自身
```

- UnionToIntersection 与逆变推断：

```ts
type UnionToIntersection<U> =
  (U extends any ? (k: U) => void : never) extends (k: infer I) => void
    ? I
    : never;

type R = UnionToIntersection<{ a: 1 } | { b: 2 }>; // { a: 1 } & { b: 2 }
```

- 推断过程分两步：
  - 第一步，`U extends any` 是分布式条件类型（裸类型参数在检查时被分发），联合 `{ a: 1 } | { b: 2 }` 被拆成两个成员，分别构造 `(k: { a: 1 }) => void` 与 `(k: { b: 2 }) => void`，结果是它们的联合。
  - 第二步，拿这个函数联合去匹配 `(k: infer I) => void`：一个函数能赋值给这个模板，当且仅当它的参数能接受模板传入的参数。两个候选都出现在参数（逆变）位置时，编译器按规则推断为所有候选的交集，否则哪个单独都不满足兼容性——于是 I 是 `{ a: 1 } & { b: 2 }`。
  - 记忆口诀：协变位置（返回值）多候选取联合，逆变位置（参数）多候选取交集。

**加分项（P7 视角）**：

- UnionToIntersection 是 Vue、Pinia、tRPC 等库实现"多模块类型自动合并"的核心：例如把多个插件类型 `Partial<Options> | ...` 翻转成 `Partial<Options1> & Partial<Options2>`，从而让最终 Options 同时拥有所有插件的字段。
- 递归类型的两个上限：栈深度（普通递归触发 "Type instantiation is excessively deep"，实例化深度上限约 50 层）；TS 4.5 引入尾递归消除——条件类型若在真分支直接返回递归调用（无额外包装），会被编译成循环，上限放宽到 1000 层。写深度递归体操时应刻意保持尾递归形式。
- Vue 的 UnwrapRef 与 DeepReadonly 同构但方向相反，且需要处理 Ref/数组/Map/Set 等特例——能指出"通用 Deep 类型在真实框架里都要为引用语义打补丁"，说明理解泛型类型的工程化代价。

## Q：条件类型与 infer 怎么用？提取 Promise 返回值、数组元素、函数参数。

**核心答案**：条件类型 `A extends B ? X : Y` 是类型层面的三元表达式；infer 在条件类型的 extends 子句中声明一个待推断的变量，编译器用模式匹配从 A 中抽出对应位置的类型。配合"裸类型参数的分发"特性，可以对联合逐成员匹配。Promise 返回值、数组元素、函数参数三个场景分别对应 infer 在返回值位置、元素位置、参数元组位置的匹配。

**知识点解析**：

- 提取 Promise 的值类型：

```ts
type PromiseValue<T> = T extends Promise<infer V> ? V : never;

type P1 = PromiseValue<Promise<number>>;          // number
type P2 = PromiseValue<Promise<number> | string>; // number | never = number（分发后 string 走 false 分支得 never）
```

- 提取数组元素（infer 在元素位置，天然支持嵌套递归展平）：

```ts
type ElementOf<T> = T extends (infer E)[] ? E : never;

type E1 = ElementOf<string[]>;    // string
type E2 = ElementOf<number[]>;    // number
type E3 = ElementOf<string[] | number[]>; // string | number：分发后各自匹配

type Flatten<T> = T extends (infer E)[] ? Flatten<E> : T;
type F1 = Flatten<[string, [number, [boolean]]]>; // 递归剥层，直到不再是数组
```

- 提取函数参数与首个参数（infer 在参数元组位置）：

```ts
type MyParameters<T> = T extends (...args: infer P) => unknown ? P : never;

type Params1 = MyParameters<(a: string, b: number) => void>; // [a: string, b: number]

type FirstArg<T> = T extends (first: infer F, ...rest: never[]) => unknown ? F : never;

type FArg = FirstArg<(a: string, b: number) => void>; // string
```

- 分发条件类型：当检查对象是"裸"类型参数（单独的 T，不是 `[T]` 或 `T[]`）且实参是联合时，会先拆成单成员分别代入。用 `[T]` 包装即可关闭分发，这是排除 never 时的常用手法：

```ts
type IsNever<T> = [T] extends [never] ? true : false;
// 若不包元组，T = never 时分发结果为 never 本身，永远拿不到 true
```

- 推断候选方向：infer 出现在协变位置（如返回值）时多候选取联合，出现在逆变位置（如参数）时取交集——这正是 UnionToIntersection 的原理（见 Q5）。
- 重载函数匹配规则：infer 匹配的是最后一个签名（官方实现如此），这是 ReturnType/Parameters 与重载交互的已知边界。

**加分项（P7 视角）**：

- infer 的本质是类型层面的"模式匹配 + 捕获变量"，等价于逻辑编程的 unification；能从"协变取联合、逆变取交集"规则讲清多候选推断，说明到了编译器推断规则层面而不仅是 API 层面。
- 尾递归条件类型（TS 4.5+）：`type Flatten<T> = T extends (infer E)[] ? Flatten<E> : T` 恰好是尾递归形式，编译器会消除递归改成循环，可用于安全处理几百层的嵌套结构而不爆栈。
- 实战场景串联：用 `Awaited` + `ReturnType` + `Parameters` 可以为请求层封装推导出"接口函数去掉 Promise 包装后的返回类型"，避免手写 DTO 重复；这是类型体操落地的最常见证明。

## Q：keyof / typeof / 索引访问类型分别做什么？as const 有什么用？

**核心答案**：keyof 取一个类型的所有键组成联合；typeof 从一个"值"反向取它的类型（类型层面的反射）；索引访问 `T[K]` 按键取出属性的类型。三者组合是"单一数据源"式类型推导的基石：一个常量对象就能同时推导出配置类型、键联合和值类型。as const 把对象/数组字面量断言为常量：所有层级加 readonly、值收窄为字面量类型，阻止字面量类型向宽类型放大（widening）。

**知识点解析**：

- 三者组合的典型链路：

```ts
const config = {
  host: 'localhost',
  port: 8080,
} as const;

type Config = typeof config; // { readonly host: "localhost"; readonly port: 8080 }
type Keys = keyof Config;    // "host" | "port"
type Host = Config['host'];  // "localhost"，而不是 string
```

- typeof 值到类型的反射：配合函数与 as const 可以从数据推导出工具类型。

```ts
const COLORS = ['red', 'green', 'blue'] as const;
type Color = (typeof COLORS)[number]; // "red" | "green" | "blue"
// typeof COLORS 是 readonly ["red", "green", "blue"]，索引 number 取出元素联合
```

- 索引访问的进阶用法：键本身可以是类型运算的结果。

```ts
type Values<T> = T[keyof T]; // 所有属性值类型的联合

type Status = { idle: 0; loading: 1; done: 2 };
type StatusValue = Values<Status>; // 0 | 1 | 2
```

- 字面量放大（widening）与 as const：可变位置的字符串字面量默认放大为 string。

```ts
let a = 'hello';        // let a: string（可变变量被放大）
const b = 'hello';      // const b: "hello"
let c = 'hello' as const; // let c: "hello"（手动阻止放大，仍不能重新赋其他字符串）
```

- as const 的两个效果必须同时理解：最深层的 readonly（递归）+ 字面量化（字符串、数字、布尔、模板字符串都收窄）。
- 函数 as const 可得到 readonly 元组签名：`const fn = ((a: string) => a.length) as const` 场景较少，更常见的是数组转元组后再做元组体操。

**加分项（P7 视角）**：

- TS 5.0 的 const 类型参数：`function first<const T extends readonly string[]>(arr: T)` 让推断阶段自动按 const 断言处理实参，等价于强制调用方写 as const，解决了"工具函数拿不到字面量元组"的老痛点。
- 表驱动架构落地：路由表、权限表、i18n 词条表用 `as const` + typeof + keyof 派生全部类型（Vue Router 的 RouteRecordMap、UnoCSS preset 的规则类型都是这个思路），新增一条配置自动获得类型提示与穷尽检查。
- widening 的编译器规则细节：字面量的"可放大类型"（fresh literal type）只在首次赋值时存在，中间变量会让新鲜性丢失——能用"新鲜度"解释 Q1 的超额属性检查与这里的放大行为，说明对类型系统一致性的理解。

## Q：协变、逆变、双变是什么？strictFunctionTypes 检查什么？any / unknown / never 的区别？

**核心答案**：协变（covariance）指子类型关系保持方向传递——Dog 是 Animal，则 `() => Dog` 可赋给 `() => Animal`（返回值位置）；逆变（contravariance）指方向翻转——`(a: Animal) => void` 可赋给 `(d: Dog) => void`（参数位置）；双变（bivariance）指两个方向都接受。strictFunctionTypes 开启后函数类型表达式的参数才做严格逆变检查，方法简写语法则豁免（保持双变，为兼容 Array 等内置类型）。any 是类型检查的完全逃逸口，unknown 是安全的 top type，never 是 bottom type。

**知识点解析**：

- 协变与逆变的判定示例：

```ts
interface Animal { name: string }
interface Dog extends Animal { breed: string }

declare const animalFn: (a: Animal) => void;
declare const dogFn: (d: Dog) => void;

const f1: (d: Dog) => void = animalFn; // OK：参数逆变（接收 Animal 的函数当然能处理 Dog）
const f2: (a: Animal) => void = dogFn; // 报错：只接收 Dog 的函数处理不了任意 Animal

declare const getDog: () => Dog;
const g1: () => Animal = getDog;       // OK：返回值协变（Dog 能当 Animal 用）
```

- 记法：函数参数逆变、返回值协变；TS 数组是协变的（历史包袱，与 Java 一样存在数组协变的隐患）。
- strictFunctionTypes 的豁免：用方法简写声明的参数不做严格检查。

```ts
interface WithMethod {
  compare(a: Animal): number; // 方法简写：双变（豁免）
}
interface WithFn {
  compare: (a: Animal) => number; // 函数属性：严格逆变
}
```

- any / unknown / never 三者对照：

```ts
let a: any = 'x';
a.foo();          // 不报错，运行时才炸——any 关闭了检查
const u: unknown = 'x';
// u.foo();       // 报错：unknown 不能直接使用
if (typeof u === 'string') u.toUpperCase(); // 收窄后可用

function fail(): never {
  throw new Error('boom');
} // never 是空集合：可赋给任何类型，但没有任何值能赋给它

type T1 = string & never; // never（与空集相交还是空集）
type T2 = string | never; // string（并上空集不变，never 在联合中被吸收）
```

- any 的特殊性：它对类型系统是双向兼容的（既是 top 又是 bottom），所以能穿透一切检查；unknown 只允许赋值和收窄，是"类型安全的 any"。
- 双变的动机：ES2015 之前 Array 的很多方法用方法签名声明，严格逆变会让旧代码大量报错，所以只对函数属性开启严格模式。

**加分项（P7 视角）**：

- 眼见为实的坑：strictFunctionTypes 关闭时 `(d: Dog) => void` 可赋给 `(a: Animal) => void`，意味着可能用 Animal 调用一个只认 Dog 的函数，运行时读 `breed` 就是 undefined——能讲出"双变是历史兼容的妥协，新代码应全量 strict"。
- unknown 的工程价值：catch 参数默认 unknown（useUnknownInCatchVariables，strict 家族成员）、API 边界收 unknown 再校验（配合 zod/valibot 的 parse 返回值类型），是"外部输入不可信"的类型化表达。
- never 的三大用途：穷尽检查的 default 分支（assertNever 模式）、过滤联合（Exclude 的实现）、永不返回的函数签名（React 的 useEffect 清理函数、类型层递归的终止哨兵）。

## Q：类型体操：手写 TupleToUnion、LengthOfString，递归类型有什么限制？

**核心答案**：TupleToUnion 用索引访问 `T[number]` 一次到位；LengthOfString 因为字符串不能用 `'length'` 取长度，必须把字符串递归拆成字符累积进元组，再用 `A['length']` 取元组长度。递归类型的两个硬限制：普通递归受实例化深度限制（约 50 层，报 "Type instantiation is excessively deep"）；TS 4.5 引入尾递归消除，条件类型在分支里直接返回递归调用时可被改写为循环，上限放宽到 1000 层。

**知识点解析**：

- TupleToUnion：元组的数字索引访问。

```ts
type TupleToUnion<T extends readonly unknown[]> = T[number];

type U1 = TupleToUnion<['a', 'b', 'c']>; // "a" | "b" | "c"
```

- 推断过程：`T[number]` 表示"用 number 类型的索引去访问 T"。对元组类型，数字索引会展开成所有位置的元素类型联合；对 `readonly` 元组同样适用，因此约束用 `readonly unknown[]` 可以同时接收可变数组与元组。

- LengthOfString：递归 + 命名元组累积器。

```ts
type LengthOfString<S extends string, A extends string[] = []> =
  S extends `${infer C}${infer R}`
    ? LengthOfString<R, [...A, C]>
    : A['length'];

type L1 = LengthOfString<'abc'>; // 3
```

- 推断过程（以 `'abc'` 为例）：
  - 第一次：模板串模式 `C R` 把 'abc' 匹配为 C = 'a'、R = 'bc'，递归调用 `LengthOfString<'bc', ['a']>`。
  - 第二次：C = 'b'、R = 'c'，递归为 `LengthOfString<'c', ['a', 'b']>`。
  - 第三次：C = 'c'、R = ''，递归为 `LengthOfString<'', ['a', 'b', 'c']>`。
  - 空串无法匹配模板（至少要一个字符），走 false 分支返回 `A['length']` 即 3。
  - 关键点：类型层面没有可变状态，所以必须用第二个默认参数 A 作为"累加器"传递中间结果，这是所有递归体操的通用模式。

- 元组长度的直接用法：

```ts
type Length<T extends readonly unknown[]> = T['length'];
type L2 = Length<['x', 'y']>; // 2（元组的 length 是字面量类型，数组的 length 是 number）
```

- 递归限制与尾递归优化：条件类型若真分支的返回值就是递归调用本身（没有再包一层对象/联合/交叉），编译器可做尾递归消除。下面的 Flip 每层递归都构造新的元组 `[...T, U]`，属于"在尾位置做参数累积"，能享受优化。

```ts
type Reverse<T extends readonly unknown[]> = T extends [infer H, ...infer R]
  ? [...Reverse<R>, H]
  : [];

type R1 = Reverse<[1, 2, 3]>; // [3, 2, 1]
```

**加分项（P7 视角）**：

- 超限的两类报错要能区分：`Type instantiation is excessively deep and possibly infinite`（深度/数量超限，通常是意外无限递归或真的太深）；`Type produces a union type that is too complex to represent`（联合成员超过 5000 万量级，常见于大规模字符串模板组合）。
- 深度递归的工程化拆法：把超大输入按段分治（如每 1000 个元素切一段分别处理再拼接），或用 tuple 拼接的合并排序式分治——参考 type-challenge 高难题的官方题解思路。
- 面试建议主动声明边界："类型体操是编译期能力的表达，但复杂类型会拖慢编译器与 IDE，团队内应限制在公共类型库，业务代码只用现成工具类型"——这句权衡话术本身就是 P7 信号。

## Q：类型收窄有哪些手段？判别联合、is 类型谓词、satisfies 分别解决什么问题？

**核心答案**：收窄（narrowing）是编译器依据控制流把宽类型逐步压缩为窄类型的过程。判别联合用字面量判别字段配合 switch/if 自动收窄；is 类型谓词让自定义函数（如 Array.isArray 式的守卫）参与收窄；satisfies（TS 4.9+）在不改变推断类型的前提下校验表达式兼容目标结构，兼得"字面量类型的精确性"与"结构约束的安全性"。

**知识点解析**：

- 判别联合（discriminated union）与穷尽检查：

```ts
interface Circle { kind: 'circle'; radius: number }
interface Rect { kind: 'rect'; w: number; h: number }
type Shape = Circle | Rect;

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.radius ** 2; // s 收窄为 Circle
    case 'rect': return s.w * s.h;                 // s 收窄为 Rect
    default: {
      const _never: never = s; // 若未来新增成员，这里编译报错，强制补分支
      throw new Error('unreachable');
    }
  }
}
```

- is 类型谓词：把运行时校验的结果告诉编译器。

```ts
function isString(x: unknown): x is string {
  return typeof x === 'string';
}

function toUpper(x: string | number) {
  if (isString(x)) return x.toUpperCase(); // x 收窄为 string
  return String(x);
}

// 实战：带守卫的过滤器
function isCircle(s: Shape): s is Circle {
  return s.kind === 'circle';
}
const circles = shapes.filter(isCircle); // Circle[]，而非 (Circle | Rect)[]
```

- satisfies 与三种替代方案的对比：

```ts
type Routes = Record<string, { path: string; method?: 'GET' | 'POST' }>;

// 1. 类型注解：失去字面量推断，route 变成宽类型
const r1: Routes = { home: { path: '/' } };
// r1.home.path 是 string，无法用于后续字面量推导

// 2. as 断言：只有断言没有校验，写错也不报错
const r2 = { home: { path: 123 } } as Routes; // 不报错，运行时才炸

// 3. satisfies：既校验又保留字面量
const r3 = { home: { path: '/' } } satisfies Routes;
type HomePath = typeof r3.home.path; // "/"，字面量被保留
```

- 常见的内置收窄手段：typeof、instanceof、in 操作符、真值收窄、相等收窄、Array.isArray；判别联合本质上是相等收窄在字面量字段上的应用。
- satisfies 的适用边界：它不做收窄，只做校验——`r3.home` 的类型仍是 `typeof r3` 推断出的字面量结构，不是 Routes。

**加分项（P7 视角）**：

- 编译器层：收窄由 checker 的控制流分析（ControlFlowGraph + TypePredicate 累积）完成；is 谓词本质是给函数签名挂上"布尔返回值与参数类型的逻辑关联"，TS 4.4+ 还支持 `x is string` 与 aliased condition（const isStr = typeof x === 'string' 提取判断变量）。
- satisfies 的杀手级场景：Vue 3.3+ 的 defineProps 泛型、对象配置表（vite.config 的插件表、路由表）——既能在 key 写错时立刻报错，又能让 `r3.home.path` 参与后续类型体操（如用 keyof typeof 生成路由名联合）。
- 守卫的完备性陷阱：is 断言编译器不校验实现逻辑（`return true` 也能通过），团队可用 type-fest 的 `Predicate` 或 zod 的 refine 保证守卫与 schema 一致；这是把"信任边界"讲成工程问题的加分点。

## Q：装饰器与 reflect-metadata 是什么关系？TS 5 装饰器和实验性装饰器有什么差异？

**核心答案**：TS 5 实现的是 TC39 Stage 3 标准装饰器，experimentalDecorators 开启的是 2015 年提案的旧版实验性装饰器，两者互不兼容。NestJS、TypeORM、Angular 生态目前仍基于旧版 + reflect-metadata polyfill（旧版会自动写入 design:type 等元数据，依赖注入靠它扫描构造参数类型）；新版装饰器是纯函数式的 API，通过 context 对象提供 kind/name/addInitializer，且不再有参数装饰器，需要元数据需自行从装饰器上下文显式写入。新项目除非绑定 NestJS 生态，否则应默认走新版。

**知识点解析**：

- 旧版（实验性）装饰器示例：类装饰器接收构造函数，可返回替换构造函数；参数装饰器与 reflect-metadata 配合实现依赖注入。

```ts
import 'reflect-metadata';

function Injectable(): ClassDecorator {
  return (target) => {
    // 旧版装饰器 + emitDecoratorMetadata 时，TS 自动写入三类元数据：
    // design:type / design:paramtypes / design:returntype
    const params = Reflect.getMetadata('design:paramtypes', target);
    console.log(params); // [Function(String)]：UserService 构造函数的参数类型
  };
}

function Inject(token: string): ParameterDecorator {
  return (target, _key, index) => {
    // Nest 的思路：把 token 注册到参数索引，实例化时从容器按序解析
    Reflect.defineMetadata(`di:param:${index}`, token, target);
  };
}

@Injectable()
class UserService {
  constructor(@Inject('logger') logger: Logger) {}
}
```

- 新版（TS 5 / Stage 3）装饰器：工厂 + 实例上下文，方法装饰器返回替换函数。

```ts
function logged<This, Args extends unknown[], R>(
  target: (this: This, ...args: Args) => R,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => R>
) {
  const name = String(context.name); // context 提供 kind/name/private/static 等元信息
  return function (this: This, ...args: Args): R {
    console.log(`before ${name}`);
    const result = target.call(this, ...args);
    console.log(`after ${name}`);
    return result;
  };
}

class Order {
  @logged
  pay(amount: number): boolean {
    return amount > 0;
  }
}
```

- 新旧差异的 5 个要点：
  - 签名不同：旧版按装饰器种类各有一套 (target, key, descriptor) 形参；新版统一为 (value, context) 二元，context 里有 kind 字段。
  - 新版没有参数装饰器，也没有 auto accessor 之外的成员描述符；旧版的 descriptor 可直接改 value/writable。
  - 元数据：旧版配合 emitDecoratorMetadata 自动注入设计期类型；新版遵循"显式优于隐式"，需要自己 defineMetadata 或等 TC39 metadata 提案落地。
  - 新版支持 accessor 关键字（auto-accessor），为字段生成 getter/setter 存储，弥补失去字段装饰器元数据能力的场景。
  - 运行时机：旧版在类定义时以属性描述符操作为主；新版装饰器在实例化/定义阶段调用，返回值即被替换的目标。

**加分项（P7 视角）**：

- reflect-metadata 是非标准的 polyfill（es-shims 之外的黑魔法），它挂在 Reflect 上扩展三个 API（defineMetadata/getMetadata/getOwnMetadata）；Nest 的依赖注入原理 = 装饰器收集元数据 + 递归按 design:paramtypes 实例化参数——能徒手画出这条链路是 DDD/Nest 岗位的硬通货。
- 生态迁移现状：NestJS 11 与 TypeORM 仍在 experimentalDecorators + legacy 路线（大量第三方库绑死旧签名）；TS 5 的默认值反转意味着新项目混用旧库时必须显式开启 experimentalDecorators + emitDecoratorMetadata，迁移策略是"新文件用新装饰器、旧域冻结"的双轨制。
- 装饰器在 5.0 的性能定位：新版装饰器可被 JIT 友好地内联，且 context 是一次性对象，框架层（如 MobX、Vue class 组件）迁移后初始化开销可测量地降低——能谈到测量与迁移成本是 P7 的工程信号。

## Q：tsconfig 里 strict 全家桶、moduleResolution、paths、isolatedModules 分别控制什么？

**核心答案**：strict 是约 10 个严格检查项的总开关，其中 strictNullChecks 是"TS 是否真正有用"的分水岭；moduleResolution 决定模块说明符如何解析为文件（node10/node16/bundler/nodenext 四种策略，bundler 是 Vite 类构建的标准答案）；paths + baseUrl 做路径别名映射（只影响类型解析，运行时仍需打包器同等配置）；isolatedModules 强制每个文件可被独立转译，是 esbuild/swc/babel 等单文件编译器的安全护栏。

**知识点解析**：

- strict 全家桶（含 4.4 追加的 useUnknownInCatchVariables）：

```jsonc
{
  "compilerOptions": {
    "strict": true
    // 等价于同时开启：
    // noImplicitAny、strictNullChecks、strictFunctionTypes、
    // strictBindCallApply、strictPropertyInitialization、noImplicitThis、
    // alwaysStrict、useUnknownInCatchVariables
  }
}
```

- 各项一句话：
  - strictNullChecks：null/undefined 不再自动并入一切类型，追查空值的成本前移到编译期。
  - noImplicitAny：隐式 any 报错，逼出参数与回调的真实签名。
  - strictFunctionTypes：函数参数逆变检查（见 Q8），方法签名豁免。
  - strictPropertyInitialization：类属性必须初始化或在构造器赋值，明确初始化语义可用 `!` 断言跳过。
  - strictBindCallApply：bind/call/apply 按真实签名校验参数。
- moduleResolution 的选型：

```jsonc
{
  "compilerOptions": {
    // "moduleResolution": "node10"  旧 CommonJS 解析（node_modules 逐级上溯、可省略扩展名）
    // "node16"/"nodenext"  按 package.json exports/imports 字段与 ESM 规则解析，要求相对导入写扩展名
    "moduleResolution": "bundler" // Vite/Webpack/esbuild 场景：支持 exports 且允许省略扩展名
  }
}
```

- paths 与运行时的关系：

```jsonc
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
// 类型层由 TS 解析；运行时必须由 Vite resolve.alias / tsconfig-paths / jest moduleNameMapper 同步实现
```

- isolatedModules 的约束清单：类型不能直接 re-export（必须 `export type`）、const enum 不允许跨文件使用（5.0 起默认报错）、每个文件必须是有效模块（有 import/export）、instanceof 无类型增强等——这些全是"单文件转译时拿不到其他文件类型信息"的直接后果。

**加分项（P7 视角）**：

- 与 isolatedModules 同族的现代项：verbatimModuleSyntax（TS 5.0）替代 importsNotUsedAsValues/preserveValueImports，让 import 语句完全按书写保留给打包器，是 esbuild/bundlers 时代的正确姿势；`module: "ESNext"` + `moduleResolution: "bundler"` 已是 Vite 官方模板默认。
- paths 的坑：paths 不影响输出代码，混合 tsc 直接跑 Node 的项目（CLI、SSR）必须用 module: node16 + 真实扩展名或 tsc-alias 处理产物；Monorepo 里更推荐 workspace 依赖 + 各包 exports 字段而不是 paths。
- 团队落地经验：strict 之外按项目补 noUncheckedIndexedAccess（索引访问带 undefined）、noFallthroughCasesInSwitch、exactOptionalPropertyTypes 三件套；渐进开启可用 @ts-expect-error 计数治理——"配置即规范"的讲述方式。

## Q：TS 的编译流程是怎样的？类型检查与转译如何分离？为什么 isolatedModules 影响打包器？

**核心答案**：tsc 编译分五步：scanner 把源码切 token → parser 生成 AST → binder 收集符号（声明与引用的绑定）→ checker 基于符号做完整类型检查 → transformer/emitter 输出 JS 与 d.ts。关键在于类型检查依赖全程序（Program）的信息，而转译单个文件理论上只需要擦除类型（types are erased）。esbuild/swc/babel 恰恰只做"单文件擦除"，不构建 Program、不做检查，速度因此快一个数量级；isolatedModules 就是把"每个文件必须能被独立擦除"变成编译期约定，保证单文件转译结果与 tsc 一致。

**知识点解析**：

- 编译流程与各步产物：

```text
Source ─scanner→ tokens ─parser→ AST ─binder→ Symbols(+AST 连接)
      ─checker(基于 Program 全量类型检查)→ 诊断
      ─transformer/emitter→ JS / .d.ts / sourcemap
```

- 类型检查只在 checker 中发生，emitter 不感知类型（TS 5 移除了基于注解的 JS 重写后更是纯擦除）；这就是"类型擦除"的实现层含义——运行时不存在任何类型信息。
- 单文件转译器的差异清单（没有 Program 后做不到的事）：
  - const enum：编译期内联其他文件里的枚举值，单文件看不到定义。
  - `export { SomeType } from './x'`：转译器不知道它是类型还是值，擦错会导致运行时 import 到不存在的东西。
  - 命名空间/参数属性（constructor(private x: T)）这类需要生成代码的语法，在跨文件引用时无法内联判断。
- isolatedModules 与打包器的关系：Vite 开发期用 esbuild 转译 TS（毫秒级），生产构建走 rollup + esbuild 插件；这条链路成立的唯一前提就是项目满足 isolatedModules 约束——所以 Vite 的默认模板全部开启它。
- 三种执行模式的取舍：

```text
tsc 全量            检查 + 转译，慢但权威（CI 的门禁）
tsc --noEmit        只检查，配合打包器做转译（最常见工程组合）
esbuild/swc/babel   只转译不检查（dev 服务器提速的关键）
```

**加分项（P7 视角）**：

- 能画出三阶段在内存里的数据结构：SourceFile（含 AST）、Symbol（含 links 缓存）、Type；checker 对每个节点的检查结果缓存在 NodeLinks，tsserver 的增量编译就是在文件级失效 + 复用这些缓存——这直接解释了"改一个文件，IDE 为什么只重检查依赖它的文件"。
- Vite dev 链路细节：esbuild 只做 TS → JS 的擦除与目标降级，esm 依赖预构建用 esbuild 打成单文件；而 vue-tsc 才是模板类型的检查者（production build 时跑 vue-tsc --noEmit），检查与转译两条线各取所长。
- P7 加分点：CI 里把 `tsc --noEmit` 与 `vite build` 并行跑（检查不阻塞产物），本地 dev 把检查交给 IDE 增量完成，构建提速 30% 以上且不牺牲类型安全——讲清"为什么可以拆开"比背流程更重要。

## Q：类型声明文件体系是怎样的？@types、declare、三斜线指令分别做什么？如何给无类型的 JS 库补类型？

**核心答案**：@types 是 DefinitelyTyped 维头的、按包名对仗的声明包仓库（@types/lodash 对应 lodash），TS 会按 typeRoots 自动加载；declare 用于声明"在别处存在、但 TS 看不见的实体"（全局变量、模块、扩展）；三斜线指令（reference path/types/lib）是 .d.ts 文件顶部的编译器依赖指令（声明文件的 import）。补类型的路径按成本递增三选一：临时 declare module 打补丁 → 完整手写 .d.ts → allowJs + 声明产出自动生成。

**知识点解析**：

- @types 的解析规则：npm install @types/lodash 后，TS 默认从 node_modules/@types 自动加载所有包；compilerOptions.types 可收窄只加载白名单，typeRoots 可改变搜索根。
- declare 的三种常见形态：

```ts
// 1. 声明全局变量（挂 window 上的第三方注入物）
declare const __APP_VERSION__: string;

// 2. 为 JS 模块补声明（模块扩充写法）
declare module 'legacy-lib' {
  export function init(options: { url: string }): void;
  const _default: { version: string };
  export default _default;
}

// 3. 扩展已有类型（为第三方库追加方法，依赖 interface 声明合并）
import 'axios';

declare module 'axios' {
  export interface AxiosRequestConfig {
    traceId?: string;
  }
}
```

- 三斜线指令（只对声明文件有意义，普通 .ts 里应用 import）：

```ts
/// <reference path="./types.d.ts" />  // 引入相对路径的声明文件依赖
/// <reference types="node" />         // 引入 node_modules/@types/node（引入 NodeJS 全局）
/// <reference lib="es2022.promise" /> // 引入内置 lib 集
```

- 为无类型 JS 库补类型的完整流程：

```ts
// step1：模块声明兜底，消除"找不到声明文件"错误
declare module 'heat-map-lib';

// step2：按真实调用面写窄声明（不要一开始就追求完备）
declare module 'heat-map-lib' {
  export interface HeatMapOptions {
    container: HTMLElement;
    data: Array<{ x: number; y: number; value: number }>;
    radius?: number;
    onRenderComplete?: (canvas: HTMLCanvasElement) => void;
  }
  export class HeatMap {
    constructor(options: HeatMapOptions);
    setData(data: HeatMapOptions['data']): void;
    destroy(): void;
  }
}

// step3：迁移为独立 heat-map-lib.d.ts + package.json 的 types 字段，回馈社区或本仓 packages/types
```

- allowJs + 自动声明产出路线：保留 JS 源码，tsc 生成 .d.ts。

```jsonc
{
  "compilerOptions": {
    "allowJs": true,
    "declaration": true,
    "emitDeclarationOnly": true,
    "outDir": "dist-types"
  }
}
```

**加分项（P7 视角）**：

- 类型解析顺序的坑：包自身有 types 字段时 @types 会被忽略；一个包同时存在"内联类型"与 @types 时按 exports/types 字段优先——排查"同一包在两个项目里类型不一致"先查这条解析链。
- JS + JSDoc 也能渐进补类型：allowJs + checkJs 时 JSDoc 的 @type/@typedef/@template 会被 TS 完整解析，可以在不重写文件的前提下获得 80% 的类型收益（Vue 2 的源码就是 JSDoc 类型化的典型案例）。
- 团队治理：给补丁型 declare module 设过期机制（TODO + issue 编号 + 定期清点），避免补丁腐化成第二个"影子 API"；私有库建议统一收敛到公司内部的 @company/types 仓，用 changesets 管理版本。

## Q：TS 编译/类型检查变慢怎么排查？project references、tsc --diagnostics 怎么用？

**核心答案**：先量化再优化：tsc --diagnostics（耗时概览）、--extendedDiagnostics（细分 scanner/parser/checker/emitter 各阶段）、--generateTrace（Chrome Tracing 可视化火焰图）三步定位瓶颈。常见慢因：巨型联合/交叉类型的实例化爆炸、第三方 d.ts 解析（skipLibCheck）、单一大 Program 全量检查。结构性优化靠 project references + composite 把大仓拆成可增量、可按需编译的子项目；代码层面减少深度递归体操、控制 any 泄漏点、收紧泛型约束复杂度。

**知识点解析**：

- 三个诊断工具：

```bash
npx tsc --noEmit --diagnostics           # Files/Lines/Identifiers/Types/Check time 总览
npx tsc --noEmit --extendedDiagnostics   # 各阶段耗时 + 类型实例数（Types count）
npx tsc --noEmit --generateTrace traces  # 导出 Chrome Tracing JSON，devtools 打开看火焰图
```

- 火焰图要看什么：最宽的 "checkSourceFile"/"getTypeOfXXX" 调用栈，反查到具体文件与类型；Types 数量异常（千万级）通常指向某个失控的条件类型或巨型 keyof 联合。
- project references 的配置：

```jsonc
// tsconfig.json（根）
{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/app" }
  ]
}

// packages/app/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,          // 声明产物 + 增量信息
    "declaration": true,
    "declarationMap": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "references": [{ "path": "../shared" }] // 声明依赖拓扑
}
```

- 构建方式变化：`tsc -b` 按引用图拓扑构建、跳过未变更的子项目（增量）；CI 与本地 dev 的提速都来自"变更隔离"——改 app 不需要重检查 shared。
- 常见代码级慢因清单：
  - 巨型 keyof/联合分发（如上千键的路由表做条件类型分发）。
  - 深度递归体操（见 Q9 的实例化深度限制，未超限也会拖慢）。
  - 未开 skipLibCheck 时全量解析 node_modules 的 d.ts（老版本 @types 的历史负担）。
  - 大量 `any` 交叉 `unknown`、重载过多的函数与宽 interface。
  - 超大单文件（几千行的类型入口文件）导致文件级缓存失效代价高。

**加分项（P7 视角）**：

- tsserver（IDE）与 tsc（CLI）的检查是两套缓存体系：IDE 卡顿优先看 project 加载策略（jsconfig/tsconfig include 范围、implicit project），VS Code 的 "TypeScript: Go to Project" 与 "Open TS Server Log" 是定位入口；同一问题在 CLI 不慢而 IDE 慢，多半是编辑器策略而非代码问题。
- 性能与表达力的权衡结论（可直接复述）：类型系统的计算复杂度是真实成本，团队规范应约定"类型体操只进内部类型包、公共 API 类型不超过两层嵌套、CI 卡点用 vue-tsc --noEmit 挂构建流水线"；把慢的排查过程固化为 lint 规则与 CI 报表（types count 基线化）是 P7 的落点。

## Q：JS 项目如何渐进式迁移到 TypeScript？

**核心答案**：核心策略是"允许混合、由外向内、先松后严"：allowJs 让 .ts 与 .js 共存于同一编译上下文，先把类型化的收益集中在公共 API 层（入口函数、核心数据模型），再逐步收紧检查等级，最后用 CI 门禁防回退。顺序上先解决依赖（换带类型的库或补 @types），再迁代码；strictNullChecks 建议放最后收口，因为它改动面最大。迁移的每一步都必须保持可发布、可回滚。

**知识点解析**：

- 阶段零：准备与依赖先行。

```jsonc
{
  "compilerOptions": {
    "allowJs": true,        // 允许混合编译，迁移期间 .js 继续工作
    "checkJs": false,       // 先不检查 JS，等核心域类型稳定后再开
    "outDir": "dist",
    "declaration": true
  }
}
```

- 阶段一：公共 API 先行——为入口、核心数据模型、工具函数写类型，收益/成本比最高：调用方立刻获得提示，内部实现迁移时有了"契约"。

```ts
// api/types.ts：先定义核心域模型（收益最大的三个文件之一）
export interface Report { id: string; title: string; data: ReportRow[] }
export type ReportRow = Record<string, string | number | null>;

// entry.ts：入口签名显式化，内部用 any 兜底
export function loadReport(id: string): Promise<Report> {
  return fetchImpl(id) as Promise<Report>;
}
```

- 阶段二：文件级渐进。改扩展名时用 @ts-nocheck 压制存量错误，再用 @ts-expect-error 逐个治理（它会在错误被修复时反向报错，天然防腐化）：

```ts
// @ts-nocheck          // 迁移当天加，治完删
import legacy from './legacy';

const data: Report[] = legacy.fetch(); // @ts-expect-error 临时豁免：待 legacy 补类型
```

- 阶段三：检查等级爬坡（每次只收紧一档，保证错误量可消化）：

```text
noImplicitAny: true
  → strictFunctionTypes、strictBindCallApply
  → strictNullChecks: true（改动面最大，压轴）
  → strict: true + noUncheckedIndexedAccess（最终态）
```

- 阶段四：CI 防回退与治理。

```jsonc
{
  "include": ["src"]
}
```

配合 lint 规则禁止新增 .js 文件、`tsc --noEmit` 进 CI、@ts-expect-error 数量纳入看板只减不增；最后移除 allowJs，迁移收官。
- JSDoc 过渡路线：无法立即改名的 JS 文件用 JSDoc 标注类型 + checkJs 局部开启，可以在零改扩展名的前提下提前获得类型检查（与 Q14 的 JSDoc 技巧同一原理）。

**加分项（P7 视角）**：

- 迁移的排序论：按"依赖图从叶子到根"或"从稳定到活跃"（活跃文件类型收益高且改动频繁）；两个流派各自适用——重构型团队选前者，业务迭代型团队选后者。能讲出自己项目里选哪个及原因即是 P7 答案。
- 度量与推进：先跑 `tsc --noEmit` 记录初始错误数作为基线（如 4000），按目录拆分到迭代任务，每周看曲线下降；错误数回涨即流水线失败——把类型迁移做成数据化运营而非情怀工程。
- 大仓与微前端场景：Wujie/NPM workspace 体系下按"子应用收敛类型边界、共享域模型下沉到 shared 包（先 d.ts 后源码）"推进；迁移期间共享包用 tsconfig composite + references 保证消费方无需等待源码级 TS 化——这是把 Q15 与本题串联的完整工程叙事。
