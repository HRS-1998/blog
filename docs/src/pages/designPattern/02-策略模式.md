# 策略模式

> 定义一系列算法，把它们一个个封装起来，并且使它们可以互相替换。

## 解决什么问题

策略模式杀的是 if-else / switch 分支爆炸。当一段逻辑里每个分支只是"算法不同"（输入输出形状一致），比如不同绩效等级算不同奖金、不同校验规则、不同缓动曲线，硬编码的分支会带来三个问题：分支会持续膨胀（新需求 = 改老函数，违反开闭原则）；函数体越来越长，没法单独测试某个算法；算法与调用逻辑耦合，无法在运行时切换。

策略模式的解法很直接：==把每个分支抽成独立、可替换的"策略"（通常就是函数或对象），调用方（Context）只持有一个策略引用，把执行委托出去。新增算法 = 新增一个策略，零侵入。==

前端里"策略表"是高频重构手段：`if (type === 'a') {...} else if (type === 'b') {...}` → `const map = { a: fnA, b: fnB }`，这其实就是策略模式的日常形态。

## 结构说明

- **Strategy（策略接口）**：所有具体策略的统一约定——同样的入参、同样的返回，保证可互换。
- **ConcreteStrategy（具体策略）**：各算法的独立实现，彼此之间互不感知、互不引用。
- **Context（上下文）**：持有某个策略的引用，把请求委托给它执行。Context 不懂算法细节，==选择哪个策略由客户端（调用方）决定==——这是它与状态模式的根本区别。

JS 里函数是一等公民，策略通常直接写成函数或函数对象，不需要像 Java 那样先定义接口。

## 原生 JS 实现

### 1. 奖金计算器（S/A/B 绩效）

```js
// 策略对象：各绩效等级的奖金算法，彼此独立
const strategies = {
  S: (salary) => salary * 5,
  A: (salary) => salary * 3,
  B: (salary) => salary * 2,
};

// Context：只管收集输入、委托计算，算法一无所知
class Bonus {
  constructor() {
    this.salary = null;
    this.strategy = null;
  }
  setSalary(salary) {
    this.salary = salary;
  }
  // 客户端选择并注入策略
  setStrategy(strategy) {
    this.strategy = strategy;
  }
  getBonus() {
    return this.strategy(this.salary); // 委托给当前策略
  }
}

// 使用
const bonus = new Bonus();
bonus.setSalary(10000);

bonus.setStrategy(strategies.S);
console.log(bonus.getBonus()); // 50000

bonus.setStrategy(strategies.A);
console.log(bonus.getBonus()); // 30000 —— 运行时随时换算法，Context 一行不改
```

对比坏味道版本——每个新等级都要改 `calculateBonus`：

```js
function calculateBonus(level, salary) {
  if (level === 'S') return salary * 5;
  else if (level === 'A') return salary * 3;
  else if (level === 'B') return salary * 2;
  // 新增 D 级？继续叠 else if……
}
```

### 2. 表单校验器（strategies + Validator）

```js
// 策略对象：每个校验规则一个策略，返回 errorMsg 表示失败，undefined 表示通过
const strategies = {
  required(value, errorMsg) {
    if (value === '' || value == null) return errorMsg;
  },
  minLength(value, length, errorMsg) {
    if (String(value).length < length) return errorMsg;
  },
  isMobile(value, errorMsg) {
    if (!/^1[3-9]\d{9}$/.test(value)) return errorMsg;
  },
};

// Context：收集规则，逐条委托策略执行
class Validator {
  constructor() {
    this.cache = []; // 待执行的校验任务队列
  }
  add(value, rules) {
    // rules 形如 [{ strategy: 'minLength:6', errorMsg: '密码至少 6 位' }]
    rules.forEach((rule) => {
      const [name, ...args] = rule.strategy.split(':');
      this.cache.push(() => {
        // 统一以 value 为首参调用策略：strategies[name](value, ...args, errorMsg)
        return strategies[name](value, ...args, rule.errorMsg);
      });
    });
  }
  validate() {
    for (const task of this.cache) {
      const errorMsg = task();
      if (errorMsg) return errorMsg; // 遇到第一条错误即返回
    }
  }
}

// 使用
const validator = new Validator();
validator.add('', [
  { strategy: 'required', errorMsg: '用户名不能为空' },
  { strategy: 'minLength:2', errorMsg: '用户名长度不能小于 2 位' },
]);
validator.add('1380013800x', [
  { strategy: 'isMobile', errorMsg: '手机号格式不正确' },
]);

console.log(validator.validate()); // '用户名不能为空'
```

新增一条"邮箱格式"校验，只需给 strategies 加一个函数，Validator 和调用代码零改动——这就是对开闭原则的支持。

## 前端中的应用

### 1. 动画缓动函数（easeIn / easeOut 策略表）

缓动算法是策略模式的经典场景：所有缓动函数签名一致 `(t) => value`，可以任意替换：

```js
const tween = {
  linear: (t) => t,
  easeIn: (t) => t * t, // 先慢后快
  easeOut: (t) => t * (2 - t), // 先快后慢
  easeInOut: (t) => (t < 0.5 ? 2 * t * t : -1 + (4 - 2 * t) * t),
};

// 动画引擎：骨架（时间推进）固定，缓动算法作为策略传入
function animate({ duration = 1000, ease = tween.easeInOut, onProgress }) {
  const startTime = performance.now();
  function render(now) {
    const t = Math.min((now - startTime) / duration, 1);
    onProgress(ease(t)); // 委托给当前缓动策略
    if (t < 1) requestAnimationFrame(render);
  }
  requestAnimationFrame(render);
}

// 切换缓动效果 = 换一个策略引用
animate({ ease: tween.easeIn, onProgress: (v) => console.log(v.toFixed(2)) });
// 输出（t 均匀递增 0.1，经 t² 映射后先慢后快）：0.00 0.01 0.04 0.09 0.16 ... 0.81 1.00
```

### 2. Vue 动态 class 与 `<component :is>`

状态 → 样式/组件的映射表，本质就是策略模式（map 替代 if-else）：

```vue
<template>
  <!-- 策略一：状态到 class 的映射，新增状态不改模板 -->
  <div :class="statusClassMap[status]">{{ status }}</div>
  <!-- 策略二：动态组件，按渠道切换支付组件 -->
  <component :is="payStrategyMap[channel]" />
</template>

<script setup>
import { ref } from 'vue';
import Alipay from './Alipay.vue';
import Wechat from './Wechat.vue';

const status = ref('loading');
const channel = ref('alipay');

const statusClassMap = {
  loading: 'is-loading',
  success: 'is-success',
  error: 'is-error',
};
const payStrategyMap = { alipay: Alipay, wechat: Wechat };
</script>
```

### 3. 消除大量 if-else（营销活动价格计算）

```js
// 重构前：3 种活动就 3 层嵌套，活动叠加后分支爆炸
function getPriceBad(type, price) {
  if (type === 'preSale') return price * 0.8;
  else if (type === 'onSale') return price > 100 ? price - 20 : price;
  else if (type === 'groupBuy') return price * 0.6;
}

// 重构后：策略表 + 兜底，新增活动只加一行
const priceStrategies = {
  preSale: (price) => price * 0.8,
  onSale: (price) => (price > 100 ? price - 20 : price),
  groupBuy: (price) => price * 0.6,
};
const getPrice = (type, price) =>
  (priceStrategies[type] ?? ((p) => p))(price); // 未知类型原价返回

console.log(getPrice('groupBuy', 100)); // 60
console.log(getPrice('unknown', 100)); // 100
```

## 优缺点与对比

**优点**：

- 消除重复的分支判断，各算法独立封装，可单独测试。
- 完美支持开闭原则：新增策略不改旧代码。
- 算法可在运行时切换（`setStrategy`），这是继承做不到的灵活性。
- 策略可复用：同一张 tween 表可以喂给任意动画函数。

**缺点**：

- 策略类/策略对象数量膨胀，小逻辑用它有杀鸡用牛刀之嫌。
- 使用方必须了解所有策略的差异才能选对——策略的"选择成本"转移给了客户端。

### 对比：策略模式 vs 状态模式（高频面试题）

两者结构几乎一样（都是 Context 持引用 + 委托），区别在意图：

| 维度 | 策略模式 | 状态模式 |
| --- | --- | --- |
| 意图 | 算法可替换，关注"怎么做" | 状态驱动行为变化，关注"处于什么阶段" |
| 策略/状态间关系 | ==各策略互不感知、互不引用== | ==各状态互相知道，能决定下一个状态== |
| 谁来切换 | 客户端主动选择并注入 | Context/状态内部自动流转，客户端不干预 |
| 运行中切换次数 | 一般切换一次（选好算法） | 随事件不断流转（红绿灯循环） |
| 典型场景 | 奖金计算、校验规则、缓动函数 | 红绿灯、订单状态机、Promise 状态 |

记忆锚点：==策略像"点菜"——客人自己选；状态像"红绿灯"——灯自己按节奏变，路人只管看。==
