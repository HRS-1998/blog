# 享元模式

> 运用共享技术有效地支持大量细粒度的对象复用——把"每个对象都一样"的部分抽出来共享，"各不相同"的部分用的时候再传。

## 解决什么问题

需要同时存在大量相似对象时的痛点：一屏弹幕几百条、一场 boss 战几百发子弹、一个长列表几万个节点。每个对象都完整地 new 一份——DOM 节点反复 createElement/appendChild/remove，内存和重排开销瞬间爆炸；纯数据对象重复携带完全相同的字段（弹幕的字号颜色、子弹的贴图尺寸），==一万条弹幕把同一份"样式信息"在内存里抄了一万遍。==

享元的解法：==把对象状态切成两半——内部状态（intrinsic，共享、不变）与外部状态（extrinsic，各自不同、用时传入）。== 内部状态只创建一份、全池共享（相同样式的弹幕共享同一个样式对象），外部状态不存进对象、每次使用时临时注入（弹幕的文本、轨道、时间戳）。再配合对象池"借出—归还"复用重资源（DOM 节点、连接），创建次数从 O(请求量) 降到 O(峰值并发量)。

一句话：==享元 = 状态拆分（省内存）+ 对象池（省创建/销毁开销）==，两招可以分开用也可以合起来用。面试里虚拟列表、连接池、弹幕池都是它的标准答案。

## 结构说明

- **Flyweight（享元对象）**：只装内部状态的角色。内部状态必须满足两点：与使用场景无关（谁用都一样）、数量有限可枚举（才能做成有限的几份共享）。
- **FlyweightFactory（享元工厂）**：维护一张"内部状态 → 享元对象"的缓存表（通常是 Map）。请求相同内部状态时返回同一个实例，==保证每种内部状态全局只有一份。==
- **Client（使用方）**：持有外部状态，从工厂按需取享元对象，把外部状态作为参数传进去完成一次"使用"。外部状态绝不写进享元对象——否则下一个使用者会读到脏数据。
- **ObjectPool（对象池，工程化形态）**：享元思想在"重资源"上的落地。`create()` 借（优先取闲置的，没有才新建），`recover()` 还（清理后放回池里待复用）。

内部状态 vs 外部状态，一张表分清：

| 维度 | 内部状态（共享） | 外部状态（不共享） |
| --- | --- | --- |
| 存在哪 | 享元对象内部，全池一份 | 使用方手里，每次用时传入 |
| 数量 | 有限、可枚举（样式、尺寸、型号） | 几乎无限（坐标、文本、时间戳） |
| 是否变化 | 对象生命周期内不变 | 每次使用都不同 |
| 弹幕例子 | 字号/颜色/边框样式 | 文本内容、轨道、出现时间 |
| 子弹例子 | 贴图/尺寸/伤害系数 | 坐标、速度、朝向 |

判断标准：==这个字段是不是"谁用都一样"？是 → 内部状态；跟每次使用绑定 → 外部状态。==

## 原生 JS 实现

### 1. 享元工厂：内部状态共享

相同样式的弹幕共享同一个样式对象，一万条弹幕只产生 3 个样式实例：

```js
// 享元工厂：key -> 享元对象，保证每种内部状态只有一份
class StyleFactory {
  constructor() {
    this.flyweights = new Map(); // '24px-#fff-bold' -> 样式对象
  }
  get(size, color, weight) {
    const key = `${size}-${color}-${weight}`;
    if (!this.flyweights.has(key)) {
      // 只有没见过的内部状态才真正创建
      this.flyweights.set(key, { size, color, weight });
      console.log(`创建新样式: ${key}`);
    }
    return this.flyweights.get(key);
  }
  count() {
    return this.flyweights.size;
  }
}

// 弹幕：样式是共享的内部状态，文本/轨道是各自持有的外部状态
class Danmaku {
  constructor(style, text, track) {
    this.style = style; // 引用同一个享元对象，不复制字段
    this.text = text;   // 外部状态：每条都不同，由使用方传入
    this.track = track;
  }
  render() {
    console.log(
      `[轨道${this.track}] ${this.text}（${this.style.size} ${this.style.color}）`
    );
  }
}

const factory = new StyleFactory();
const danmakus = [];
// 一万条弹幕，样式只有 3 种预设
const presets = [
  { size: '32px', color: '#fff' },
  { size: '24px', color: '#ff0' },
  { size: '32px', color: '#ff0' },
];
for (let i = 0; i < 10000; i++) {
  const { size, color } = presets[i % 3];
  const style = factory.get(size, color, 'bold');
  danmakus.push(new Danmaku(style, `弹幕#${i}`, i % 10));
}

console.log(factory.count()); // 3 —— 一万条弹幕，样式对象只有 3 份
danmakus[0].render(); // [轨道0] 弹幕#0（32px #fff）
danmakus[1].render(); // [轨道1] 弹幕#1（24px #ff0）
```

==内部状态的数量取决于组合数（预设数），与对象总量无关==——这就是省内存的来源。

### 2. 对象池：借出—归还复用重资源（弹幕/子弹）

DOM 节点是典型的重资源。对象池的契约：==用完不销毁，还回去给下一个人用；创建次数只取决于峰值并发，不取决于总请求量。==

```js
// 通用对象池：create 借（优先闲置，没有才新建），recover 还（下屏、清理后入池）
class ObjectPool {
  constructor(factory, reset = () => {}) {
    this.factory = factory; // 池空时才调用的创建工厂
    this.reset = reset;     // 归还时的清理函数：抹掉外部状态防脏数据
    this.idle = [];         // 闲置对象栈（后进先出，缓存友好）
    this.total = 0;         // 累计创建数，观察复用效果
  }
  create() {
    if (this.idle.length > 0) {
      return this.idle.pop(); // 池里有闲置的，直接复用
    }
    this.total++; // 只有池空才真正创建
    return this.factory();
  }
  recover(obj) {
    obj.remove?.(); // DOM 节点池：归还先从页面上摘下，闲置节点不该继续留在 body 里
    this.reset(obj); // 关键：清掉上一任留下的外部状态
    this.idle.push(obj);
  }
}

// 子弹池：div 节点是重资源，create/appendChild 越少越好
const bulletPool = new ObjectPool(
  () => document.createElement('div'),
  (el) => {
    el.className = ''; // 清理外部状态，避免下个使用者读到脏数据
    el.style.transform = '';
  }
);

// 发射一批子弹：借节点、注入外部状态（坐标）、上屏
function shoot(targets) {
  return targets.map(({ x, y }) => {
    const el = bulletPool.create(); // 从池里借
    el.className = 'bullet';        // 注入本次的外部状态
    el.style.transform = `translate(${x}px, ${y}px)`;
    document.body.appendChild(el);
    return el;
  });
}

let bullets = shoot([
  { x: 10, y: 20 },
  { x: 30, y: 40 },
]);
console.log(bulletPool.total); // 2 —— 创建了 2 个节点

// 飞出屏幕：还回池里（recover 会先把它从页面上摘下），而不是销毁再重建
bullets.forEach((el) => bulletPool.recover(el));

bullets = shoot([
  { x: 50, y: 60 },
  { x: 70, y: 80 },
  { x: 90, y: 100 },
]);
console.log(bulletPool.total); // 3 —— 前两个复用，只有第三个是新建的
```

验证：第一次 shoot 借 2 个（池空，total 1→2）；全部还回后池里有 2 个闲置；第二次 shoot 3 发：前 2 发从池里 pop 复用，第 3 发池空新建（total 2→3）。==打了一万发子弹，DOM 节点数只等于同屏峰值==——这就是 FPS 游戏弹幕不掉帧的秘密。

## 前端中的应用

### 1. 虚拟列表：滚动复用 DOM 节点（核心思想即享元）

10 万条数据的长列表，直接渲染就是 10 万个 DOM 节点——必卡死。虚拟列表（vue-virtual-scroller / react-virtualized / Element Plus 的 el-table-v2）的解法完全就是享元：

- 内部状态（共享）：DOM 节点本身——一个"行"的外壳（结构、样式）在滚动过程中被反复复用；
- 外部状态（每次注入）：`startIndex` 对应的那条数据，滚到哪就往复用的节点里塞哪条的 props；
- 对象池：可视区域外多渲染几屏的缓冲区，滚出去的节点还回缓冲区，滚进来的从缓冲区借。

```js
// 极简示意：固定行高的虚拟列表，只维护可视区域的一撮节点
function virtualList(container, data, rowHeight = 40) {
  const viewportH = container.clientHeight;   // 视口高度
  const visibleCount = Math.ceil(viewportH / rowHeight) + 2; // +2 缓冲
  container.style.overflow = 'auto';
  container.innerHTML = '';

  const sizer = document.createElement('div');
  sizer.style.height = `${data.length * rowHeight}px`; // 撑出总滚动高度
  const screen = document.createElement('div');
  screen.style.position = 'relative'; // 节点们绝对定位，靠 translateY 摆到行位置
  // screen（0 高定位层）必须在前：贴住容器顶部，行才从 y=0 处渲染；sizer 在后只负责撑滚动条
  container.append(screen, sizer);

  container.addEventListener('scroll', () => {
    const start = Math.floor(container.scrollTop / rowHeight);
    // 节点不够才补，够就复用——总节点数永远 ≈ visibleCount
    while (screen.children.length < visibleCount) {
      const row = document.createElement('div');
      row.style.position = 'absolute';
      row.style.height = `${rowHeight}px`;
      screen.appendChild(row);
    }
    // 外部状态注入：滚到哪行，就把哪行的数据塞进复用的节点
    for (let i = 0; i < visibleCount; i++) {
      const item = data[start + i];
      const el = screen.children[i];
      el.textContent = item?.name ?? '';
      el.style.transform = `translateY(${(start + i) * rowHeight}px)`;
    }
  });
  container.dispatchEvent(new Event('scroll')); // 初始渲染一次
}
// 10 万行数据，屏幕上永远只有 ~20 个 div
```

### 2. HTTP keep-alive / 数据库连接池

网络连接是比 DOM 更重的"对象"：TCP 三次握手 + TLS 握手 + 慢启动，一次请求一套的开销不可接受。HTTP/1.1 Keep-Alive 让==多个请求复用同一条 TCP 连接==；Node 的 `http.Agent` 内部就是一个连接池（`maxSockets` 控制池大小）；后端的数据库连接池、Redis 连接池同理——连接创建一次，请求来了从池里借，用完还回：

```js
// Node：http.globalAgent 就是一个连接池
// keepAlive: true 后，对同一 host 的请求复用已建立的 socket
const http = require('node:http');
const agent = new http.Agent({ keepAlive: true, maxSockets: 10 });
http.request({ host: 'api.example.com', agent, path: '/a' }); // 建连 + 请求
http.request({ host: 'api.example.com', agent, path: '/b' }); // 复用同一条连接
```

浏览器侧同理：同一域名下并发的几个请求共用握手好的 TCP/TLS 连接（Chrome 的连接池按 origin 管理）。==面试问"keep-alive 是什么"，可以答：连接层面的享元/对象池。==

### 3. 引擎内置的享元：字符串驻留与小整数

享元在 JS 引擎里是有"官方实现"的。字符串字面量会被引擎驻留（interning）——==相同内容的字面量全程序共享同一份存储==，两处写 `'hello'` 只有一份字符串数据：

```js
const a = 'hello';
const b = 'hello';
console.log(a === b); // true —— 值相等（字符串比较本来就是值语义）
// 但多数引擎（V8）字面量确实指向同一块驻留内存，这就是共享
```

数字侧：V8 用 SMI（Small Integer）直接把小整数编码进指针位，==不装箱、不堆分配==，"每个 5 都是同一个 5"，可以理解为引擎内置的享元。Java 的 `IntegerCache`（-128~127 缓存 Integer 对象）是这个思想的教科书实现。这些是引擎实现细节、不该依赖它做恒等判断（`===` 对字符串/数字本来就是值比较），但用来理解"共享以省内存"的动机非常直观。

## 优缺点与对比

**优点**：

- 内存占用大幅下降：同种内部状态只存一份，万级对象秒变个位数实例。
- 创建/销毁开销大幅下降：对象池复用重资源（DOM、连接、WebGL 纹理），GC 压力小。
- 峰值资源占用可控：同屏多少对象，就创建多少，与总量无关。

**缺点**：

- ==状态拆分提高复杂度==：内部/外部状态的划分需要设计判断，外部状态传参让调用代码变啰嗦。
- 池化带来生命周期管理成本：忘还 → 内存泄漏；还之前没 reset → 脏数据串场；并发场景还要考虑借还的竞态。
- 享元对象被多方共享，==必须保持无状态（对外部状态而言）==，一旦偷偷存了外部状态就全乱。

### 对比：享元 vs 单例（都是"共享实例"）

区别在"共享几份、为的是啥"，详见[单例模式](./01-单例模式.md)：

| 维度 | 单例模式 | 享元模式 |
| --- | --- | --- |
| 实例数量 | 全局恰好 1 个 | ==每种内部状态一份==（N 种就 N 个） |
| 共享目的 | 全局状态一致性（大家看到同一份数据） | 减少重复创建、省内存 |
| 状态语义 | 实例携带核心业务状态（store 的 state） | 实例对外部状态必须无状态 |
| 获取方式 | getInstance 静态访问点 | 享元工厂按内部状态取 |
| 典型场景 | 全局 store、全局弹窗 | 对象池、虚拟列表、连接池 |

一句话背下来：==单例是"全班只有一台投影仪"，享元是"每种教材只印一本，全班传着看"。== 也可以说享元是"把单例从'一个类一个实例'泛化到'一种内部状态一个实例'"的池化。

## 相关模式：池化与享元的关系

工程语境里"对象池"和"享元"经常混用，精确地说：==享元是模式（共享内部状态），对象池是实现手段（借出—归还复用）。== 池子里的对象不一定拆内外状态（比如纯粹的 dom 池），拆了状态不配池也成立（样式工厂）；弹幕系统两个都要：样式工厂管"少创建几种"，对象池管"创建的这几个反复用"。
