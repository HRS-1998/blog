# 模板方法模式

> 在父类中定义一个算法的骨架（固定流程与顺序），将其中某些步骤延迟到子类实现，使得子类可以在不改变算法结构的情况下重定义算法的某些步骤。

## 解决什么问题

多个类共享"同一套流程，但各步骤细节不同"时的痛点：咖啡和茶的冲泡流程完全一样（烧水 → 冲泡 → 倒杯 → 加料），只有"冲泡"和"加什么料"不同。各写各的实现，流程代码复制两份——==流程（不变）和步骤细节（变）搅在一起==，哪天流程要求加一步"摇晃均匀"（如第四步），所有类都要改，漏改一个就行为不一致。

模板方法的解法：==把不变的骨架放进基类，把可变的步骤声明成"空位"交给子类填。== 流程顺序只在基类出现一次，子类只负责实现细节；改流程只动基类，加实现只加子类——变与不变被一条线切开。

它的精神是==好莱坞原则："别调用我们，我们会调用你"==（Don't call us, we'll call you）：控制权在基类（框架）手里，子类（开发者）只提供被调用的实现——这正是所有前端框架生命周期的底层隐喻。

## 结构说明

- **AbstractClass（抽象基类）**：定义模板方法（骨架，如 `init` 按固定顺序调用各步骤）+ 一批步骤方法。Java 里模板方法标 `final` 防止子类篡改流程，JS 没有 final，靠约定。
- **基本方法（具体步骤）**：三类——
  - **具体方法**：基类已实现、子类直接继承（如"把水烧开"，人人一样）；
  - **抽象方法**：基类只声明，==强制子类实现==（JS 无接口，用"抛错的默认实现"模拟）；
  - **钩子方法**：基类给默认实现（通常返回 true/false），子类可选择性覆写，==用来影响骨架中可选步骤的执行与否==——不改骨架也能插手流程分支。
- **ConcreteClass（具体子类）**：填空。只实现抽象方法、按需覆写钩子。

## 原生 JS 实现

冲饮料：骨架 `boilWater → brew → pourInCup → addCondiments` 固定，子类只实现 brew / addCondiments，钩子控制"要不要加料"：

```js
// 抽象基类：骨架与不变步骤都在这里
class Beverage {
  // 模板方法：固定流程与顺序 —— 子类不应覆写（约定上的 final）
  init() {
    this.boilWater();
    this.brew(); // 空位1：抽象方法，子类必须实现
    this.pourInCup();
    if (this.customerWantsCondiments()) { // 钩子：控制可选步骤
      this.addCondiments(); // 空位2：抽象方法
    }
  }
  // 具体方法：所有饮料通用，子类直接继承
  boilWater() {
    console.log('把水烧开');
  }
  pourInCup() {
    console.log('倒进杯子');
  }
  // 抽象方法：JS 没有接口，用抛错的默认实现逼子类实现
  brew() {
    throw new Error('子类必须实现 brew()');
  }
  addCondiments() {
    throw new Error('子类必须实现 addCondiments()');
  }
  // 钩子方法：默认加料，子类可覆写为 false 跳过该步骤
  customerWantsCondiments() {
    return true;
  }
}

// 具体子类：只填空，不碰流程
class Coffee extends Beverage {
  brew() {
    console.log('用沸水冲泡咖啡');
  }
  addCondiments() {
    console.log('加糖和牛奶');
  }
  // 覆写钩子：这杯咖啡不加料 —— 没改一行骨架代码，却改变了流程走向
  customerWantsCondiments() {
    return false;
  }
}

class Tea extends Beverage {
  brew() {
    console.log('用沸水浸泡茶叶');
  }
  addCondiments() {
    console.log('加柠檬');
  }
  // 不覆写钩子 → 沿用默认（加料）
}

const coffee = new Coffee();
coffee.init();
// 把水烧开
// 用沸水冲泡咖啡
// 倒进杯子
// （钩子返回 false，跳过"加糖和牛奶"）

const tea = new Tea();
tea.init();
// 把水烧开
// 用沸水浸泡茶叶
// 倒进杯子
// 加柠檬
```

现代 JS 更常用==高阶函数替代继承==实现同一结构——骨架在闭包里固定，空位由参数传入，组合优于继承：

```js
// 函数式模板方法：流程仍是固定骨架，"子类"变成了配置对象
function makeBeverage({ brew, addCondiments, wantsCondiments = () => true }) {
  return function run() {
    console.log('把水烧开');
    brew();
    console.log('倒进杯子');
    if (wantsCondiments()) addCondiments();
  };
}

const tea = makeBeverage({
  brew: () => console.log('用沸水浸泡茶叶'),
  addCondiments: () => console.log('加柠檬'),
});
tea();
// 把水烧开
// 用沸水浸泡茶叶
// 倒进杯子
// 加柠檬
```

## 前端中的应用

### 1. Vue/React 生命周期：框架级模板方法（最典型）

生命周期是前端最大的模板方法现场，==框架是抽象基类，你写的组件是具体子类==。以 Vue 为例：实例化的骨架（初始化数据与响应式 → 挂载渲染 → 依赖更新 → 卸载清理）由框架定死，开发者只能往固定"空位"里填函数：

```js
// 你在"填空"，时机与顺序永远轮不到你决定
export default {
  created() {
    // 空位1：数据初始化后、DOM 生成前 —— 只能在这拿数据，拿不到 $el
  },
  mounted() {
    // 空位2：DOM 挂载后 —— 能拿到 $el、初始化图表/监听
  },
  unmounted() {
    // 空位3：销毁前 —— 清定时器、解绑全局监听
  },
};
```

三个关键点（面试表述）：

- ==流程控制权在框架==：created 一定先于 mounted，你在 mounted 里写代码不能让它提前执行——好莱坞原则的字面演绎。
- Vue3 的 `onMounted(() => {...})` 只是换了填空姿势：注册回调，时机仍由框架调度，语义完全一致。
- React 类组件同理（`componentDidMount` 等），而且 `render()` 就是典型的"抽象方法"——基类声明、子类必须实现。Vue 源码里 `callHook(vm, 'mounted')` 的调用链，就是把模板方法里的"空位调用"落到了实处。

### 2. Express/Koa：请求处理的固定骨架

Koa 源码（v2 简化）里处理请求的模板方法——`createContext → 中间件链 → handleResponse / onerror`，骨架不给你改，你能做的只是往中间件链里"填"函数：

```js
// Koa：骨架在框架源码里，简化如下
handleRequest(ctx, fnMiddleware) {
  onFinished(ctx.res, ctx.onerror);      // 步骤1：兜底错误处理
  fnMiddleware(ctx)                       // 步骤2：执行你填的中间件链
    .then(() => respond(ctx))             // 步骤3：统一响应
    .catch(ctx.onerror);
}

// 开发者视角：只能在"中间件"这个空位里做文章
app.use(async (ctx, next) => {
  console.log('前置逻辑');
  await next(); // 流程推进点在框架手里 —— 你决定不了链的走向，只能决定自己这段做什么
  console.log('后置逻辑');
});
```

`await next()` 前后能写什么、整条链何时启动、响应何时发出，全是框架的模板方法说了算。

### 3. 脚手架 CLI：固定初始化流程

create-vue / create-vite 这类脚手架的主流程是标准模板方法：==询问 → 生成 → 安装 → 初始化 git==，顺序固定；变的只是"按什么答案生成哪些文件"：

```js
// create-vue 主流程（简化）：每一步都可能按用户答案走不同分支，但流程本身不变
async function create(projectName) {
  const answers = await askQuestions(); // 1. 询问：要 TS 吗？要 ESLint 吗？
  generateFiles(projectName, answers);  // 2. 按答案拷贝/渲染模板文件
  await installDeps(projectName);       // 3. npm install
  initGit(projectName);                 // 4. git init + 首次提交
}
```

如果再加一步"提示下一步命令"（步骤 5），只改这个骨架函数一处；每个模板包只负责"generateFiles 怎么生成"，完全不感知流程——变与不变各归其位。

## 优缺点与对比

**优点**：

- ==变与不变分离==：流程只在基类出现一次，改流程一处生效，子类零感知。
- 子类只填空，实现成本极低；框架可以强制约束"空位"的时机（生命周期语义由此而来）。
- 钩子方法给了子类影响流程的口子，又不用开放骨架的修改权。

**缺点**：

- 依赖继承（类实现），子类与父类强耦合——父类改动波及所有子类（白盒复用）。
- 骨架被隐藏在基类里，读子类代码看不到完整流程，必须翻父类。
- 每种变化都要派生子类，变化组合多时子类数量爆炸（函数式写法可缓解）。

### 对比：模板方法 vs 策略模式（高频混淆）

两者都是"封装变化"，但变化的粒度与手段完全不同：

| 维度 | 模板方法 | 策略模式 |
| --- | --- | --- |
| 变化粒度 | ==换骨架中的个别步骤==，流程结构不变 | ==整个算法整体替换==，没有固定骨架 |
| 实现手段 | ==继承==：子类覆写空位方法 | ==组合==：Context 注入策略对象 |
| 流程控制权 | 基类（好莱坞原则） | 客户端（自己挑策略） |
| 复用方式 | 白盒复用（子类需了解父类结构） | 黑盒复用（策略只需遵守接口约定） |
| 典型场景 | 生命周期、请求处理骨架、CLI 流程 | 奖金计算、校验规则、缓动函数 |

一句话背下来：==模板方法是"填空题"——骨架印在卷子上，你只填空；策略是"选择题"——整道算法挑一个换上去。== 组合优于继承，所以工程里策略更常见，但只要存在"固定的流程骨架"（生命周期、中间件），模板方法就是唯一答案。
