# 中介者模式

> 用一个中介对象封装一系列对象的交互，使各对象之间不需要显式地相互引用，从而耦合松散、可以独立变化。

## 解决什么问题

多个对象之间有业务互动时的通病：每个对象都得持有"所有协作方"的引用才能完成一次交互。三个用户聊天，每人要认识另外两人；五个页面共享登录态，每个页面要认识另外四个——==对象数量每加一，连接数按 N(N-1) 暴涨，整个系统织成一张网，删一个对象、改一个方法签名，全网抖动。==

中介者的解法：==把所有"对象认识对象"的网状依赖，收拢成"大家只认识中介者"的星形结构。== 交互双方不再直接调用，统一经过中介者转发、协调。新增一个参与者只需向中介者注册，其他参与者零改动。

代价也直白：中介者会逐渐吸收所有协作细节，==网状耦合被搬进了一个类的肚子里——中介者本身可能膨胀成"上帝对象"==，这正是它和发布订阅模式经常一起出现、互相稀释复杂度的原因（文末对比）。

## 结构说明

- **Mediator（中介者）**：核心角色。持有所有同事对象的注册表，定义"谁的消息发给谁"的协调规则；同事之间的交互全部由它转发或裁决。
- **Colleague（同事对象）**：参与交互的各方。只持有中介者的引用，需要通信时把请求交给中介者，==绝不直接持有其他同事==。
- **交互流程**：Colleague A → `mediator.send(...)` → Mediator 按自己的规则决定通知谁、是否过滤 → 逐个调用目标 Colleague 的接收方法。A 到 B 的"双向认知"变成"A 认识中介者、中介者认识 B"。

关键理解：中介者不是简单的"转发管道"，它==懂业务规则==——谁能和谁说话、消息要不要过滤、要不要拦截，这些规则写在中介者里，而不是散落在各同事的代码里。

## 原生 JS 实现

### 坏例子先看：用户两两直连（网状耦合）

```js
// 每个 User 持有"所有其他用户"的引用，自己遍历、自己分发
class User {
  constructor(name) {
    this.name = name;
    this.others = []; // 认识名单：人数越多越失控
  }
  addOther(user) {
    this.others.push(user);
  }
  send(message) {
    // 自己决定发给谁：规则散落在每个 User 里
    this.others.forEach((user) => user.receive(this.name, message));
  }
  receive(from, message) {
    console.log(`${this.name} 收到 ${from} 的消息: ${message}`);
  }
}

const alice = new User('Alice');
const bob = new User('Bob');
const carol = new User('Carol');

// 上线时两两握手：3 人共 6 次注册，N 人要 N(N-1) 次
alice.addOther(bob); alice.addOther(carol);
bob.addOther(alice); bob.addOther(carol);
carol.addOther(alice); carol.addOther(bob);

alice.send('大家好');
// Bob 收到 Alice 的消息: 大家好
// Carol 收到 Alice 的消息: 大家好
```

第 4 个人 Dave 进来，3 个老用户全要改代码注册他；想做"敏感词过滤"，得改每个 User 的 send——这就是网状耦合的账单。

### 中介者版本：聊天室

```js
// 中介者：聊天室。持有所有用户，定义转发规则
class ChatRoom {
  constructor() {
    this.users = new Map(); // 注册表：name -> user
  }
  join(user) {
    this.users.set(user.name, user);
  }
  leave(user) {
    this.users.delete(user.name);
  }
  // 群发：转发给除发送者外的所有人（规则写在中介者里）
  broadcast(from, message) {
    this.users.forEach((user) => {
      if (user.name !== from) user.receive(from, message);
    });
  }
  // 私聊：定向转发。同事完全不知道这个逻辑的存在
  whisper(from, to, message) {
    this.users.get(to)?.receive(from, message);
  }
}

// 同事对象：只认识中介者，发消息一律交给它
class User {
  constructor(name, room) {
    this.name = name;
    this.room = room; // 唯一的依赖
    room.join(this); // 向中介者注册
  }
  send(message) {
    this.room.broadcast(this.name, message);
  }
  sendTo(to, message) {
    this.room.whisper(this.name, to, message);
  }
  receive(from, message) {
    console.log(`${this.name} 收到 ${from} 的消息: ${message}`);
  }
}

// 使用：注册关系全自动，新增用户对老人零改动
const room = new ChatRoom();
const alice = new User('Alice', room);
const bob = new User('Bob', room);
const carol = new User('Carol', room);

alice.send('大家好');
// Bob 收到 Alice 的消息: 大家好
// Carol 收到 Alice 的消息: 大家好

bob.sendTo('Alice', '悄悄说');
// Alice 收到 Bob 的消息: 悄悄说（Carol 无感知）
```

需求变更最能体现价值——加敏感词过滤和踢人，==只改 ChatRoom 一个类，User 和所有调用代码零改动==：

```js
// 在 ChatRoom 里加黑名单（constructor 里 this.blacklist = new Set()）
// 并升级 broadcast：过滤敏感词、剔除黑名单
broadcast(from, message) {
  const safe = message.replaceAll('笨蛋', '**'); // 过滤规则集中管理
  this.users.forEach((user) => {
    if (user.name !== from && !this.blacklist.has(user.name)) {
      user.receive(from, safe);
    }
  });
}
```

## 前端中的应用

### 1. Vuex/Redux 全局 store：组件间通信的中介者

没有 store 时，跨层级组件通信要 `$emit` 层层上抛、props 层层下钻，或兄弟组件借助共同父级中转——组件之间形成隐式的网状依赖。引入 store 后，==所有组件只与 store 对话：改状态走 dispatch，读状态走订阅，组件之间互不认识==：

```js
// store 是唯一中介者：reducer 里写着所有协调规则
const store = createStore((state = { count: 0 }, action) => {
  switch (action.type) {
    case 'INCREMENT': return { count: state.count + 1 };
    default: return state;
  }
});

// 组件 B（响应方）：只订阅 store，不认识 A
store.subscribe(() => console.log('B 重新渲染:', store.getState().count));

// 组件 A（发起方）：只 dispatch，不认识 B
store.dispatch({ type: 'INCREMENT' }); // B 重新渲染: 1
store.dispatch({ type: 'INCREMENT' }); // B 重新渲染: 2
```

Vuex 的 `commit/dispatch`、Pinia 的 `store.xxx` 同理：==中介者模式 + 发布订阅（subscribe 通知）的组合==是全局状态库的标准内核。

### 2. antd Form：表单字段状态的中介者

`<Form.Item>` 数十个字段组件之间互不引用，但联动（省市区级联、某字段变化触发另一个校验）、统一校验、提交收集全部需要"跨字段协作"。antd 的做法是 Form 组件充当中介者：每个 Field 注册到 FormStore，值变化上报给 Form，由 Form 决定通知哪些依赖字段、何时触发校验：

```jsx
const [form] = Form.useForm(); // 拿到中介者的控制句柄

<Form form={form} onFinish={(values) => console.log(values)}>
  {/* Field 只和 Form 交互，互相之间完全解耦 */}
  <Form.Item name="province">...</Form.Item>
  {/* district 声明依赖 province：联动规则由 Form 裁决，字段间无引用 */}
  <Form.Item name="district" dependencies={['province']}>...</Form.Item>
</Form>

// 提交时不需要组件自己收集：Form（中介者）统一汇总所有字段
form.validateFields().then((values) => console.log(values));
// { province: '浙江', district: '西湖区' }
```

不用 Form 时手写这些：`useState` 十几个 + 手动同步联动 —— 就是"字段两两直连"的网状坏味道。

### 3. 小程序/多页面之间通信

小程序页面栈里的页面互相拿不到稳定引用，硬来只能 `getCurrentPages()[0].setData(...)` —— 下标耦合、页面一关就崩。惯用解法是让 App 实例充当全局中介者：

```js
// app.js —— App 是全局唯一中介者
App({
  globalData: { userInfo: null },
});

// 页面 A（登录页）：只向中介者写，不认识任何页面
getApp().globalData.userInfo = { name: 'ct' };

// 页面 B（个人页）：onShow 时只向中介者读
onShow() {
  console.log(getApp().globalData.userInfo?.name); // 'ct'
}
```

多页应用（MPA）、iframe 之间同理：直连不可行时，都是引入一个双方都够得着的中间层（全局对象、postMessage 目标、storage + 事件）来协调。

## 优缺点与对比

**优点**：

- 网状依赖 → 星形依赖，同事对象可独立开发、测试（mock 一个中介者即可）。
- 协作规则集中在一处，改规则（过滤、拦截、定向）不动同事。
- 新增/移除参与者只涉及注册，符合开闭原则。

**缺点**：

- ==中介者吸收所有协作细节，容易膨胀成上帝对象，它自己反而变成最难维护的类。==
- 同事与中介者互相持有引用（双向耦合），与发布订阅"谁也不认识谁"相比解耦不彻底。
- 交互链路绕经中介者，调试时跳来跳去，直接调用关系的可读性更好。

### 对比：中介者 vs 发布订阅（高频混淆）

两者都有"中心"，结构图几乎一样，区别在中心的职责与通信方向：

| 维度 | 中介者模式 | 发布订阅模式 |
| --- | --- | --- |
| 中心角色 | ==参与业务、懂协调规则==（谁能发给谁、要不要过滤） | 纯转发管道，不懂业务，只按事件名分发 |
| 通信方向 | ==双向==：同事调中介者，中介者反向调用同事 | ==单向==：发布者 → 中心 → 订阅者，到订阅者为止 |
| 双方认知 | 同事知道中介者的存在（持有引用） | 发布/订阅双方连彼此存在都不必知道 |
| 消息目标 | 中介者裁决谁接收（可定向私聊、可拦截） | 无差别广播给所有订阅者 |
| 中心复杂度 | 集中业务规则，可能变上帝对象 | 永远薄（一张事件表），复杂度在事件设计上 |
| 典型场景 | 聊天室、Redux store、antd Form | EventBus、mitt、DOM 事件 |

一句话背下来：==中介者是"机场塔台"——飞机不互相喊话，全听塔台调度，塔台认识每架飞机；发布订阅是"公众号"——作者发完就走，谁看到全凭订阅，平台不认识任何人。== 工程实践里两者常组合出现：Redux 既是组件通信的中介者，内部又用订阅机制通知更新。
