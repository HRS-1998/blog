# 单例模式

> 保证一个类只有一个实例，并提供一个访问它的全局访问点。

## 解决什么问题

全局只需要一份的东西，如果每次使用都 `new` 一个，会带来两类问题：一是重复创建开销（一个 Modal 组件要重复挂载 DOM、重复绑定事件）；二是状态不一致（两个 Loading 实例各自维护计数器，无法正确判断"所有请求都结束了"）。

直觉解法是挂全局变量，但全局变量极易被覆盖、污染命名空间，且无法延迟创建（脚本一加载就初始化，哪怕用户全程没用到）。==单例模式的核心价值：把"唯一性"这件事从使用方的自觉，收敛到类自身（或一个通用函数）里，使用方想创建第二个都创建不出来。==

前端里单例的出场率极高：全局弹窗、全局 store、ES Module 的 import 缓存，本质上都是单例。面试常问"你项目里的单例"，答案基本都藏在这几个场景里。

## 结构说明

- **Singleton（单例类）**：持有唯一的实例引用，构造逻辑写在自己内部。
- **getInstance（访问点）**：静态方法或闭包函数，判断实例是否已存在——存在直接返回，不存在先创建再缓存。
- **Client（使用方）**：永远通过 `getInstance` 拿实例，不直接 `new`。

关键点是把"管理实例"与"业务逻辑"分离：

- 惰性单例：第一次使用才创建（区别于脚本加载即创建的"饿汉式"），JS 里闭包让这件事非常自然。
- 通用化：把"保证唯一"抽成独立的 `getSingle` 高阶函数，任何创建函数都能复用，符合单一职责原则。

## 原生 JS 实现

### 1. class static + getInstance

```js
class GlobalLoading {
  constructor() {
    if (GlobalLoading.instance) {
      // 防止绕过 getInstance 直接 new 出第二个
      return GlobalLoading.instance;
    }
    this.count = 0; // 计数器：并发请求共享同一个状态
    this.el = null;
    GlobalLoading.instance = this;
  }

  mount() {
    if (!this.el) {
      this.el = document.createElement('div');
      this.el.className = 'global-loading';
      document.body.appendChild(this.el);
    }
    this.count++;
    this.el.style.display = 'block';
  }

  unmount() {
    this.count = Math.max(0, this.count - 1);
    if (this.count === 0) this.el.style.display = 'none';
  }

  // 全局访问点
  static getInstance() {
    if (!GlobalLoading.instance) {
      GlobalLoading.instance = new GlobalLoading();
    }
    return GlobalLoading.instance;
  }
}

const a = GlobalLoading.getInstance();
const b = GlobalLoading.getInstance();
console.log(a === b); // true —— 永远是同一个对象
console.log(new GlobalLoading() === a); // true —— 直接 new 也被拦截
```

### 2. 闭包版（经典 IIFE 写法）

```js
const Singleton = (function () {
  let instance = null; // 闭包私有的实例引用，外部无法篡改
  return function createSingleton(name) {
    if (!instance) {
      instance = { name, createdAt: Date.now() };
    }
    return instance;
  };
})();

const s1 = Singleton('config');
const s2 = Singleton('other');
console.log(s1 === s2); // true
console.log(s1.name); // 'config' —— 第二次的参数被忽略，因为实例早已创建
```

### 3. 惰性单例通用函数 getSingle（重点，源自旧笔记）

上面的写法把"单例管理"和"具体业务"耦在一起。更优的做法是把惰性单例抽成通用高阶函数——==单一职责原则的教科书应用：createIframe 只管创建，getSingle 只管唯一。==

```js
var getSingle = function (fn) {
  var result; // 闭包缓存第一次的执行结果
  return function () {
    // 第一次：result 为 undefined，执行 fn 并缓存
    // 之后：直接返回缓存，fn 不再执行
    return result || (result = fn.apply(this, arguments));
  };
};

// 使用：iframe 动态创建（如富文本编辑器、第三方登录弹层）
var createIframe = getSingle(function () {
  var iframe = document.createElement('iframe');
  document.body.appendChild(iframe);
  return iframe;
});

createIframe(); // 创建 iframe，返回 DOM
createIframe(); // 直接返回上一次的 iframe，不会重复创建
```

注意一个细节：`result || (result = fn(...))` 在 fn 返回 falsy 值（如 0、''）时会重复执行，更严谨的写法：

```js
var getSingle = function (fn) {
  var result;
  var invoked = false;
  return function () {
    if (!invoked) {
      result = fn.apply(this, arguments);
      invoked = true;
    }
    return result;
  };
};
```

## 前端中的应用

### 1. 全局唯一的 Loading / Modal 弹窗

```js
const createModal = function (text) {
  const div = document.createElement('div');
  div.className = 'modal';
  div.innerHTML = text;
  div.style.display = 'none';
  document.body.appendChild(div);
  return div;
};

const getSingleModal = getSingle(createModal);

// 多个按钮点击、多处业务代码调用，DOM 里始终只有一个 .modal
function openToast(text) {
  const modal = getSingleModal(text);
  modal.innerHTML = text; // 复用同一节点，只改内容
  modal.style.display = 'block';
}
```

第一次调用才创建（惰性），之后每次复用同一个 DOM 节点——这正是 Element Plus / Ant Design 的 `ElMessage`、`message.success()` 全局唯一提示的实现思路（内部维护单例队列 + 复用容器）。

### 2. Vuex / Pinia 的 store 是单例

```js
// Vuex 4 源码（简化）：install 时把 store 挂到 app 上，全应用共享一个 store
app.use(store) // store.install 内部 app.config.globalProperties.$store = store

// Pinia 同理：所有组件 import 的 useUserStore() 拿到的是同一份 state
const userStore = useUserStore(); // 不同组件调用，返回同一个 store 实例
```

如果 store 不是单例，A 组件改了状态 B 组件看不到，响应式全局状态管理就失效了。

### 3. ES Module 天然单例（面试高频）

```js
// counter.js
export const state = { count: 0 }; // 模块顶层只执行一次

// a.js
import { state } from './counter.js';
state.count = 1;

// b.js
import { state } from './counter.js';
console.log(state.count); // 1 —— 无论多少文件 import，拿到的都是同一份
```

==ES Module 的加载机制：模块代码在首次 import 时执行一次，之后所有 import 都从缓存（Module Record）中取同一个实例。== 所以"模块即单例"，这是现代前端里最省事、也最常用的单例实现方式——根本不用写 getInstance。

## 优缺点与对比

**优点**：

- 内存中只有一个实例，避免重复创建/销毁带来的开销（尤其 DOM 节点、WebSocket 连接等重资源）。
- 提供受控的全局访问点，比裸全局变量安全（不可被随意覆盖）。
- 全局状态集中：Loading 计数器、store 等需要"多处共享一份状态"的场景天然合适。

**缺点**：

- 单例 = 全局状态，模块间形成隐式耦合，==不利于单元测试==（测试间相互污染，无法隔离 mock，需要额外提供 reset/destroy 能力）。
- 违反单一职责的倾向：既管业务又管自己的生命周期。
- 不适用于需要多实例的相似对象场景（此时应换工厂模式）。

### 对比：单例 vs 工厂模式

| 维度 | 单例模式 | 工厂模式 |
| --- | --- | --- |
| 实例数量 | 全局恰好 1 个 | 按需创建 N 个 |
| 关注点 | "怎么保证唯一、何时创建（惰性）" | "怎么创建、创建哪个子类" |
| 返回值 | 永远返回同一引用 | 每次通常返回新对象 |
| 典型前端场景 | store、全局弹窗、ES Module | `createElement`、组件工厂 |

一句话：==单例管"唯一"，工厂管"批量与解耦"。==

## 相关模式：工厂模式

工厂模式的核心是**把 new 的过程封装起来，让使用方不依赖具体类**。分三种，逐级抽象：

**1. 简单工厂**：一个函数 + 分支，按参数返回不同产品。弹窗类型工厂：

```js
class Modal {
  constructor(title) {
    this.title = title;
  }
}
class ConfirmModal extends Modal {}
class AlertModal extends Modal {}

// 简单工厂：根据 type 决定实例化哪个类
const modalFactory = (type, title) => {
  switch (type) {
    case 'confirm':
      return new ConfirmModal(title);
    case 'alert':
      return new AlertModal(title);
    default:
      throw new Error(`未知的弹窗类型: ${type}`);
  }
};

modalFactory('confirm', '确认删除？'); // ConfirmModal 实例
```

缺点：新增类型要改工厂函数的 switch，违反开闭原则。

**2. 工厂方法**：把"创建哪个类"下放到子类，每个具体工厂只造一种产品：

```js
class ModalFactory {
  create(title) {
    throw new Error('抽象方法，子类必须实现');
  }
}
class ConfirmFactory extends ModalFactory {
  create(title) {
    return new ConfirmModal(title);
  }
}

new ConfirmFactory().create('确认删除？'); // 新增类型只需加新工厂，不改旧代码
```

**3. 抽象工厂**：对"产品族"的抽象——工厂不再造单个产品，而是造一族相关产品（如一个 UI 主题工厂同时产出 Button + Input + Modal）。

前端里最著名的工厂：React 的 `React.createElement(type, props, ...children)` 就是工厂函数——根据 type（字符串 → 原生元素 / 函数或类 → 组件）创建不同类型的 ReactElement；Vue 的 `h()` 同理。
