# 代理模式

> 为一个对象提供一个代用品或占位符，以便控制对它的访问。

## 解决什么问题

代理解决的痛点是：调用方需要"使用"某个对象，但直接访问它有代价或不安全——图片太大直接 setSrc 会白屏闪烁、昂贵计算重复执行、敏感接口不该被任何角色随意调。又不想改被访问对象的代码，也不想改调用方的写法。

代理的解法：在调用方和目标对象之间插一层"长得一模一样"的代理对象，==接口签名与本体完全相同，调用方无感知==。代理可以在转发前后插入控制逻辑：延迟加载（虚拟代理）、结果缓存（缓存代理）、权限拦截（保护代理）、合并请求、埋点日志等。

与适配器/装饰者的关键区分：代理提供**相同的接口**（调用方感觉不到代理的存在），适配器提供**不同的接口**（明知要转换），装饰者提供**增强后的接口**（明知在加料）。

## 结构说明

- **RealSubject（本体）**：真正干活的对象，如真实加载图片的类、真实计算函数。
- **Proxy（代理）**：持有一个本体的引用，对外暴露与本体相同的接口；调用它的方法，实际是代理先做控制（预加载/缓存/鉴权），再转给本体。
- **Client（调用方）**：面对代理编程，就像面对本体编程一样。

代理的三种常见类型：

- **虚拟代理**：把"昂贵创建"延迟到真正需要的时刻（图片懒加载最典型）。
- **缓存代理**：相同入参直接返回缓存结果，跳过本体执行。
- **保护代理**：访问前校验权限/条件，不满足则拦截。

## 原生 JS 实现

### 1. 虚拟代理：图片懒加载（placeholder → onload 换真图）

```js
// 本体：直接设置 src
class PreloadImage {
  constructor(imgNode) {
    this.imgNode = imgNode;
  }
  setSrc(src) {
    this.imgNode.src = src;
  }
}

// 虚拟代理：先上占位图，真图加载完成再替换
class ProxyImage {
  static LOADING_URL =
    'data:image/svg+xml;base64,PHN2ZyB4bWxucz0iaHR0cDovL3d3dy53My5vcmcvMjAwMC9zdmciLz4='; // 极小的 base64 占位图
  constructor(imgNode) {
    this.realImage = new PreloadImage(imgNode);
  }
  // 与本体同名同参的接口——调用方无感知
  setSrc(src) {
    this.realImage.setSrc(ProxyImage.LOADING_URL); // 1. 先显示占位图
    const virtualImg = new Image(); // 2. 借一个离屏 Image 预加载真图
    virtualImg.onload = () => {
      this.realImage.setSrc(src); // 3. 加载完成才切换，避免长时间白块
    };
    virtualImg.src = src;
  }
}

// 使用
const img = document.querySelector('#avatar');
const proxyImage = new ProxyImage(img);
proxyImage.setSrc('https://cdn.example.com/big-photo.png');
// 效果：#avatar 先显示占位图，真图 onload 后替换 src
```

### 2. 缓存代理：计算结果 Map 缓存

```js
// 本体：昂贵的递归计算
function fib(n) {
  return n <= 1 ? n : fib(n - 1) + fib(n - 2);
}

// 缓存代理工厂：包一层，同参直接命中缓存
const createCacheProxy = (fn) => {
  const cache = new Map();
  return function (...args) {
    const key = args.join(',');
    if (!cache.has(key)) {
      cache.set(key, fn.apply(this, args));
    }
    return cache.get(key);
  };
};

const proxiedFib = createCacheProxy(fib);

console.time('first');
proxiedFib(30); // 真实计算
console.timeEnd('first'); // first: ~15ms（机器而异）

console.time('second');
proxiedFib(30); // 命中缓存，本体不再执行
console.timeEnd('second'); // second: ~0.01ms
```

同一个工厂可以代理任意纯函数——分页请求缓存、计算属性缓存都是这个套路。

### 3. 保护代理：权限校验拦截（ES6 Proxy 版）

```js
// 本体：敏感的订单操作
const orderService = {
  deleteOrder(orderId) {
    console.log(`订单 ${orderId} 已删除`);
    return true;
  },
};

// 保护代理：get 时包一层函数，先校验权限再放行
const orderServiceProxy = new Proxy(orderService, {
  get(target, prop) {
    const fn = target[prop];
    if (typeof fn !== 'function') return fn;
    return function (...args) {
      if (currentUser.role !== 'admin') {
        console.warn('无权限执行该操作'); // 实际项目：抛错 / 跳登录
        return false; // 拦截，不转发给本体
      }
      return fn.apply(target, args); // 校验通过才转发
    };
  },
});

// 使用
let currentUser = { role: 'guest' };
orderServiceProxy.deleteOrder(1001); // 无权限执行该操作

currentUser = { role: 'admin' };
orderServiceProxy.deleteOrder(1001); // 订单 1001 已删除
```

## 前端中的应用

### 1. Vue3 响应式：new Proxy 是代理模式的官方落地

Vue2 用 `Object.defineProperty` 逐属性劫持（要遍历、无法监听新增属性）；Vue3 直接用 `Proxy` 代理整个对象，get 时收集依赖（track），set 时派发更新（trigger）——==响应式系统本质就是代理模式：组件操作的是代理对象，本体是原始数据，中间层负责"访问控制+副作用"。==

```js
// Vue3 reactive 的极简示意（真实实现在 @vue/reactivity）
const targetMap = new WeakMap(); // target -> Map<key, Set<effect>>

function track(target, key) {
  let depsMap = targetMap.get(target);
  if (!depsMap) targetMap.set(target, (depsMap = new Map()));
  let dep = depsMap.get(key);
  if (!dep) depsMap.set(key, (dep = new Set()));
  dep.add(activeEffect); // 收集当前正在执行的副作用（渲染函数/computed）
}

function trigger(target, key) {
  const dep = targetMap.get(target)?.get(key);
  if (dep) dep.forEach((effect) => effect()); // 挨个执行订阅的副作用
}

function reactive(obj) {
  return new Proxy(obj, {
    get(target, key) {
      track(target, key); // 读取时：依赖收集
      return target[key];
    },
    set(target, key, value) {
      target[key] = value;
      trigger(target, key); // 写入时：派发更新
      return true;
    },
  });
}

let activeEffect = null;
const state = reactive({ count: 0 });
activeEffect = () => console.log('视图更新:', state.count); // 模拟渲染函数
state.count = 1; // 视图更新: 1
```

### 2. 防抖节流的本质是代理

防抖/节流不改变原函数的签名与职责，只是包一层控制访问频率的壳，调用方照常调用——这正是代理的定义：

```js
// 缓存代理思想的近亲：控制"访问频率"
function debounce(fn, delay) {
  let timer = null;
  return function proxy(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay); // 拦截+延迟转发
  };
}

// 搜索框防抖：调用方无感知，以为自己在调 search
const search = debounce((kw) => console.log('请求:', kw), 300);
search('j'); search('ja'); search('jav'); // 300ms 内只发一次 → 请求: jav
```

### 3. 辨析：nginx 反向代理不是本模式

面试容易踩坑：运维语境的"反向代理"（nginx 把请求转发给上游服务器）是**网络架构概念**，不是 GoF 设计模式。它解决的通信问题而非对象访问控制问题，没有接口一致性可言。==如果面试官问"反向代理是不是代理模式"，正确姿势：概念同源（都有"中间人"），但 nginx 反向代理是系统间通信拓扑，设计模式的代理是对象级别控制访问。== 前端真正要会的是 Proxy 对象（Vue3 响应式）与代理模式思想（防抖节流、缓存、鉴权）。

## 优缺点与对比

**优点**：

- 职责清晰：代理负责控制，本体负责业务，符合单一职责。
- 调用方无感知：接口与本体一致，可随时插入/移除代理层。
- 智能化：延迟加载、缓存、合并请求、鉴权，都能提升性能与安全性。

**缺点**：

- 请求经过中间层转发，响应速度略降、调用栈变深。
- 代理层与本体接口要保持同步，接口变了代理要跟着改。
- 层次多了难调试（一个响应式 bug 可能要在代理栈里翻半天）。

### 对比：代理模式 vs 装饰者模式（结构双胞胎）

两者都是"包一层、转发"，区分点在意图与感知：

| 维度 | 代理模式 | 装饰者模式 |
| --- | --- | --- |
| 意图 | ==控制访问==（拦截/延迟/缓存/鉴权） | ==增强功能==（加日志、加计时、加边框） |
| 对调用方 | 无感知，常以为在用本体 | 明知在叠加能力，按需层层包裹 |
| 与本体关系 | 代理通常**先于**本体存在，替它"看门" | 装饰者**依赖**已有本体，往上加料 |
| 数量 | 一般一层代理 | 可多层嵌套（withLog(withTiming(fn))） |
| 典型前端场景 | Vue3 reactive、防抖节流、图片懒加载 | HOC、高阶函数包装、TS 装饰器 |

记忆锚点：==代理是"保安"——管你能不能进；装饰者是"手机壳"——让你更好用，但机还是那台机。==
