# 命令模式

> 将一个请求封装成一个对象，从而使你可以用不同的请求对客户进行参数化，并对请求进行排队、记录、撤销等操作。

## 解决什么问题

"发起请求的一方"和"真正干活的一方"直接耦合的痛点：工具栏按钮的 click 回调里直接写死业务逻辑，想给同一逻辑绑个快捷键要复制一遍；想做撤销（Ctrl+Z），发现"操作已经执行完了、过去了就是过去了"，没有任何东西留下来供你回退。

命令模式的解法：==把"请求"本身封装成对象（带 execute 方法），发起方只管拿到命令对象调用 execute，不认识执行者，更不接触执行细节。== 请求一旦是对象，就能被存储（撤销栈）、排队（任务队列）、序列化（redux action 的 JSON）、组合（宏命令）——==撤销/重做的能力正是"请求对象化"送来的==，这是它区别于其他模式的招牌能力。

前端日常最常碰到的形态：redux 的 action 就是命令的 JSON 描述（详见应用一节）。

## 结构说明

- **Command（命令接口）**：统一约定 `execute()`，需要撤销能力时再加 `undo()`。
- **ConcreteCommand（具体命令）**：持有接收者（Receiver）引用，execute 把活派给接收者的方法；undo 实现逆向操作。
- **Invoker（调用者）**：持有命令对象，在恰当时机（点击、快捷键）调用 `command.execute()`。==只认命令接口，不认识接收者==。
- **Receiver（接收者）**：真正干活的对象（编辑器、播放器）。

关键认知：==调用者 → 命令 → 接收者，两层都是单向的==。按钮不知道"加粗"怎么实现，"加粗"命令不知道自己是被按钮还是快捷键触发的——两端各自变化互不影响。

## 原生 JS 实现

### 1. 命令对象与调用者（最小形态）

```js
// 具体命令：持有接收者（电视），execute/undo 互为逆操作
class PowerCommand {
  constructor(tv) {
    this.tv = tv;
  }
  execute() {
    this.tv.on();
  }
  undo() {
    this.tv.off();
  }
}

// 接收者：只提供原始能力，不知道命令的存在
class TV {
  on() { console.log('电视开机'); }
  off() { console.log('电视关机'); }
}

// 调用者：遥控器按钮只认命令接口
class Button {
  setCommand(command) {
    this.command = command;
  }
  click() {
    this.command.execute();
  }
}

const tv = new TV();
const button = new Button();
button.setCommand(new PowerCommand(tv));
button.click(); // 电视开机
```

按钮和电视互不认识，中间隔着一个命令对象——换一个命令（音量+）按钮代码零改动。

### 2. 撤销/重做：富文本编辑器（两栈是核心）

规则背下来：==执行 → 入 undo 栈 + 清空 redo 栈；undo → 从 undo 栈弹出、执行其 undo、压入 redo 栈；redo → 从 redo 栈弹出、执行其 execute、压回 undo 栈==：

```js
// 具体命令：插入文本，undo 为精确截掉这段
class InsertTextCommand {
  constructor(editor, text) {
    this.editor = editor;
    this.text = text;
  }
  execute() {
    this.editor.content += this.text; // 正向：追加
  }
  undo() {
    this.editor.content = this.editor.content.slice(0, -this.text.length); // 逆向：截掉
  }
}

// 调用者 + 历史管理：两栈撑起 Ctrl+Z / Ctrl+Y
class Editor {
  constructor() {
    this.content = '';
    this.undoStack = [];
    this.redoStack = [];
  }
  executeCommand(command) {
    command.execute();
    this.undoStack.push(command); // 执行过的进 undo 栈
    this.redoStack = []; // 关键：新命令让 redo 分支作废（未来已被改写）
  }
  undo() {
    const command = this.undoStack.pop();
    if (!command) return console.log('没有可撤销的操作');
    command.undo();
    this.redoStack.push(command); // 撤销的进 redo 栈
  }
  redo() {
    const command = this.redoStack.pop();
    if (!command) return console.log('没有可重做的操作');
    command.execute();
    this.undoStack.push(command); // 重做回来，重回 undo 栈
  }
}

const editor = new Editor();
editor.executeCommand(new InsertTextCommand(editor, '你好'));
editor.executeCommand(new InsertTextCommand(editor, '，'));
editor.executeCommand(new InsertTextCommand(editor, '世界'));
console.log(editor.content); // 你好，世界

editor.undo(); // 撤销「世界」
console.log(editor.content); // 你好，

editor.undo(); // 撤销「，」→ '你好'
editor.redo(); // 重做「，」
console.log(editor.content); // 你好，

// 招牌行为：插入新命令后，redo 栈被清空
editor.undo(); // 撤销「，」→ content = '你好'
editor.executeCommand(new InsertTextCommand(editor, '!')); // content = '你好!'
console.log(editor.content); // 你好!
editor.redo(); // 没有可重做的操作（旧「世界」「，」的回退路径已作废）
```

逐栈走一遍（面试常要求手推）：三条命令后 `undoStack=[你好,，,世界]`；撤销两次后 `undoStack=[你好]`、`redoStack=[世界,，]`；重做一次后 `undoStack=[你好,，]`、`redoStack=[世界]`；再撤销一次回到 `undoStack=[你好]`、`redoStack=[世界,，]`；此时执行新命令 `!`，==redoStack 被清空==——因为"未来"已经被新输入改写，重做旧的会得到错误结果。

### 3. 宏命令：命令数组顺序执行、逆序撤销

```js
// 宏命令：一组命令打包成一条命令，对外仍是普通命令
class MacroCommand {
  constructor(commands) {
    this.commands = commands;
  }
  execute() {
    this.commands.forEach((cmd) => cmd.execute()); // 顺序执行
  }
  undo() {
    // 撤销必须逆序：后执行的先撤，否则状态对不上
    [...this.commands].reverse().forEach((cmd) => cmd.undo());
  }
}

// 「插入问候语」= 三条插入命令的宏（换个干净的编辑器演示）
const editor2 = new Editor();
const greet = new MacroCommand([
  new InsertTextCommand(editor2, '你好'),
  new InsertTextCommand(editor2, '，'),
  new InsertTextCommand(editor2, '世界'),
]);

editor2.executeCommand(greet); // 对编辑器而言它就是一条命令
console.log(editor2.content); // 你好，世界
editor2.undo(); // 宏整体撤销：逆序撤掉三段
console.log(JSON.stringify(editor2.content)); // ""（宏内三条命令全部撤空）
```

宏命令对调用者完全透明——它实现了 execute/undo，就能进任何命令栈，==这也是"组合"能力的来源：命令可以嵌套命令==。逆序撤销是正确性前提：如果顺序撤，第一个 `undo('你好')` 从尾部截掉的其实是后执行的「世界」——中间状态全错，纯追加场景只是最终结果侥幸一致；一旦命令是定点插入、删除等位置敏感操作，==不逆序必然得到错误状态==。

## 前端中的应用

### 1. 编辑器撤销：Ctrl+Z 的原理

浏览器 input 原生就带 undo 栈（输入后按 Ctrl+Z 能逐字回退，中途再输入则 redo 分支失效——正是上面两栈逻辑）；富文本编辑器（Quill / ProseMirror / Slate）的 history 模块是工业级实现：把每次文档变更包成命令压栈，undo 时反向应用变更。Quill 甚至提供了 `editor.history.undo()` 这样的显式命令入口——=="操作可撤销"从来不是免费的，它是把操作对象化存下来的回报==。

### 2. 菜单/按钮统一派发命令

工具栏二十个按钮，与其给每个按钮写一份 click 处理器，不如==按钮只携带命令名、点击统一派发==。命令与触发源解绑后，同一命令可以同时挂到工具栏、快捷键、右键菜单：

```js
// 命令注册表：所有触发源共用一份
const commands = {
  bold: {
    title: '加粗',
    shortcut: 'Ctrl+B',
    execute: () => document.execCommand('bold'),
  },
  copy: {
    title: '复制',
    execute: () => navigator.clipboard.writeText(getSelection().toString()),
  },
};

// 工具栏：按钮只带 data-command，点击统一派发
document.querySelector('.toolbar').addEventListener('click', (e) => {
  const { command } = e.target.dataset;
  commands[command]?.execute(); // 一个入口，所有按钮共用
});

// 快捷键：与按钮触发同一条命令，零重复代码
window.addEventListener('keydown', (e) => {
  if (e.ctrlKey && e.key === 'b') commands.bold.execute();
});
```

VSCode 的 `commands.registerCommand` + `keybindings.json` 就是这个架构：命令是第一等公民，按钮/快捷键/命令面板只是不同的触发入口。

### 3. Redux action：命令的 JSON 描述

`{ type: 'ADD_TODO', payload: { text: '学命令模式' } }` 完全符合命令模式的定义——==把请求封装成纯数据对象，dispatch(action) 即"执行"，reducer 是真正的执行者==。它比 class 形态的命令更极端：连方法都没有，只是命令的"描述"，执行逻辑全在 reducer。这样做的回报：

- ==action 可序列化==，于是能被记录、传输、回放——Redux DevTools 的"时间旅行调试"就是把历史 action 队列存下来，逐个重放给一个空 reducer。
- 命令队列、重放、乐观更新等中间件（redux-undo）都建立在这层"请求对象化"之上。

```js
// dispatch 即执行命令，action 就是命令对象的 JSON 形态
store.dispatch({ type: 'todos/add', payload: { text: '学命令模式' } });
store.getState(); // { todos: [{ text: '学命令模式' }] }
```

## 优缺点与对比

**优点**：

- 发起者与执行者彻底解耦，命令可复用在多个触发源（按钮/快捷键/菜单）。
- ==请求对象化带来增值能力：撤销/重做、排队、日志、序列化回放==——这是它独有的招牌。
- 宏命令让命令可组合，新命令不改旧结构，符合开闭原则。

**缺点**：

- 每个操作一个命令类，数量膨胀；简单场景直接调函数更清爽。
- 命令对象持有接收者引用，浅拷贝/序列化时要注意闭包与引用陷阱（所以 redux 干脆把命令做成纯数据）。

### 对比：命令 vs 发布订阅

两者都能解耦"发起方"和"干活方"，但通信模型完全不同：

| 维度 | 命令模式 | 发布订阅模式 |
| --- | --- | --- |
| 通信模型 | ==点对点==：调用者持有明确的命令对象 | ==广播==：发布者不知道谁在听、有几个听 |
| 接收方数量 | 一个明确的执行者 | 任意多个订阅者 |
| 撤销/排队/记录 | ==原生支持==（命令可存栈、可序列化） | 事件发出去即结束，无撤销语义 |
| 返回值/后续 | 可拿到执行结果、可链式撤销 | 单向通知，不关心订阅者做了什么 |
| 典型场景 | 撤销栈、工具栏命令、redux action | EventBus、mitt、DOM 事件 |

一句话背下来：==命令是"下指令"——派给谁、怎么撤销都清清楚楚；发布订阅是"发广播"——喊一嗓子就走，谁听见、干了什么一概不管。== 需要追溯和回退选命令，需要多方响应选订阅。
