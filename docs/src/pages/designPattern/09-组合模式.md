# 组合模式

> 将对象组合成树形结构以表示"部分-整体"的层次，使得客户端对单个对象和组合对象的使用具有一致性。

## 解决什么问题

处理树形结构数据时的痛点：文件系统里的"文件"和"文件夹"、菜单里的"菜单项"和"子菜单"、组织架构里的"员工"和"部门"——==容器（有子项）和叶子（无子项）本质是两种东西，但客户端希望用同一种方式对待它们==。不用组合模式的写法：每个递归处都要 `if (child.isDirectory) {...} else {...}`，遍历逻辑与类型判断搅在一起，新增一种节点类型（如快捷方式、软链接），所有遍历函数全部要改。

组合模式的解法：==让叶子和容器实现同一个接口，容器的方法内部递归调用子项的同类方法。== 客户端拿到任何节点，调用方式完全一致；递归在容器里展开，在叶子上自然终止。类型判断彻底消失，"整体"的行为就是"部分"行为的聚合。

一句话：==它把"递归遍历树"这件事从客户端代码搬进了结构本身==。

## 结构说明

- **Component（组件接口）**：叶子和容器的统一约定（如 `scan`），客户端只依赖它。
- **Leaf（叶子）**：树的最末端，没有子项，接口方法是它的最终行为。
- **Composite（容器）**：持有子项列表（子项既可以是叶子也可以是容器），接口方法里==先做自己的事，再把请求委托给所有子项递归处理==。容器里"长着容器"就是树。

实现上的经典取舍（面试加分）：

- **透明方式**：叶子也声明 add/remove（统一接口完整），但调用时抛错——好处是客户端无需判断类型，代价是叶子背着无意义的方法。
- **安全方式**：只有容器有 add/remove——叶子干净，但客户端想建树时得先确认手里是容器（又回到类型判断）。

## 原生 JS 实现

文件目录树：Folder 和 File 实现同一个 `scan` 接口，Folder 递归调用子项：

```js
// 叶子：文件。scan 是最终行为，也是递归的终止条件
class File {
  constructor(name) {
    this.name = name;
  }
  scan(depth = 0) {
    console.log(`${'  '.repeat(depth)}文件: ${this.name}`);
  }
}

// 容器：文件夹。持有一个子项列表，子项可以是 File 也可以是 Folder
class Folder {
  constructor(name) {
    this.name = name;
    this.children = [];
  }
  add(child) {
    this.children.push(child);
    return this; // 链式建树
  }
  // 同一接口：先处理自己，再把请求递归分给每个子项
  scan(depth = 0) {
    console.log(`${'  '.repeat(depth)}目录: ${this.name}`);
    this.children.forEach((child) => child.scan(depth + 1));
  }
}

// 建树：容器套容器，结构任意深
const components = new Folder('components');
components.add(new File('Button.vue')).add(new File('Input.vue'));

const utils = new Folder('utils');
utils.add(new File('format.js'));

const root = new Folder('src');
root.add(new File('main.js')).add(components).add(utils);

// 客户端：一个 scan() 打穿整棵树，没有任何 if (是文件还是目录)
root.scan();
// 目录: src
//   文件: main.js
//   目录: components
//     文件: Button.vue
//     文件: Input.vue
//   目录: utils
//     文件: format.js
```

"统一对待"的威力——从树里任取一个节点，不关心它是叶子还是容器，用法一致：

```js
const node = root.children[1]; // 拿到的是 Folder；换成 children[0]（File）用法不变
node.scan();
// 目录: components
//   文件: Button.vue
//   文件: Input.vue
```

对比不用组合的坏味道——类型判断与遍历逻辑缠在一起，每种节点类型一个分支：

```js
// 坏味道：每个操作都要重新写一遍"判断类型 + 分开处理"
function scanBad(node, depth = 0) {
  if (node.type === 'file') {
    console.log('  '.repeat(depth) + node.name);
  } else if (node.type === 'folder') {
    console.log('  '.repeat(depth) + node.name + '/');
    node.children.forEach((child) => scanBad(child, depth + 1));
    // 新增"软链接"类型？这里加 else if，且每个类似函数都要加一遍
  }
}
```

## 前端中的应用

### 1. DOM 树：Node 体系的天然组合

DOM 是组合模式教科书级实现：Element、Text、Comment、Document 全部实现统一的 Node 接口（cloneNode、parentNode、childNodes……），==遍历 childNodes 时不需要为"文本节点还是元素节点"写分支==：

```js
const app = document.querySelector('#app');

// childNodes 里混着元素节点、文本节点、注释节点，统一按 Node 对待
[...app.childNodes].forEach((node) => node.cloneNode()); // 每种 Node 都有 cloneNode

// appendChild 接受任何 Node 类型 —— 接口统一，容器操作不挑子项
const frag = document.createDocumentFragment();
frag.appendChild(document.createTextNode('文本叶子'));
frag.appendChild(document.createElement('div')); // 元素子树
app.appendChild(frag);
```

React/Vue 的虚拟 DOM 同理：组件 vnode 与原生元素 vnode 是同一套结构（type/props/children），diff 算法递归 children 时统一处理，==能在组件位置渲染原生元素、在原生元素下挂组件，靠的就是"叶子与容器同构"==。

### 2. 框架渲染：children 的递归处理

简化版 vnode 渲染——组件节点（容器）执行后得到子树继续递归，原生元素（叶子）创建真实 DOM：

```js
// 简化示意：不处理 props/diff，只看递归结构
function renderVNode(vnode) {
  if (typeof vnode.type === 'function') {
    // 容器节点：执行组件函数得到子树，递归处理 —— 组件里还能是组件
    return renderVNode(vnode.type());
  }
  // 叶子节点：创建真实 DOM，挂载 children
  const el = document.createElement(vnode.type);
  vnode.children?.forEach((child) => el.appendChild(renderVNode(child)));
  return el;
}
```

组件树可以任意深度嵌套而渲染代码不变——这正是组合模式"整体与部分一致"的收益。

### 3. 递归组件：MenuTree 菜单树

无限层级菜单是组合模式最贴近业务的前端形态——==一个组件同时充当叶子和容器的渲染器，通过递归自身处理任意深度==：

```vue
<!-- MenuTree.vue -->
<template>
  <ul>
    <li v-for="item in items" :key="item.key">
      {{ item.label }}
      <!-- 容器行为：有 children 就递归渲染自己；叶子（无 children）自然终止 -->
      <MenuTree v-if="item.children?.length" :items="item.children" />
    </li>
  </ul>
</template>

<script setup>
// Vue3 的 <script setup> 中，组件默认可用文件名在模板里引用自身
defineOptions({ name: 'MenuTree' }); // 显式命名更稳，防止重构文件名后递归失效
defineProps({
  items: { type: Array, default: () => [] },
});
</script>
```

使用（数据长什么样，树就渲染多深）：

```vue
<MenuTree :items="menuItems" />

<script setup>
import { ref } from 'vue';

const menuItems = ref([
  {
    key: 1,
    label: '指南',
    children: [
      { key: 11, label: '安装' }, // 叶子
      { key: 12, label: '介绍' }, // 叶子
    ],
  },
  {
    key: 2,
    label: 'API',
    children: [
      { key: 21, label: '响应式', children: [{ key: 211, label: 'ref' }] }, // 容器套容器
    ],
  },
]);
</script>
```

==MenuTree 里没有一行"这是目录还是菜单项"的判断==——`v-if="item.children?.length"` 就是叶子与容器的分界，递归深度由数据决定。要加"展开/收起"，给 item 加个 `open` 字段控制 `v-if` 即可，结构不变。VitePress/Element 的无限级菜单、el-cascader 级联选择器都是这个原理。

## 优缺点与对比

**优点**：

- ==客户端对叶子与容器一视同仁，所有类型判断消失==，遍历代码极简。
- 新增节点类型只需实现接口，无需改动任何已有遍历逻辑，符合开闭原则。
- 与树形结构（DOM、组件树、菜单树）天然契合，前端处处是它的舞台。

**缺点**：

- 透明方式下叶子被迫实现容器方法（add/remove 抛错），接口不"纯净"；安全方式又把类型判断还给客户端——两难。
- 很难限制容器里能装什么（类型系统不介入时，Folder 里塞进一个数字也不会报错）。

### 对比：组合 vs 职责链

两者都是"节点转发请求"，但结构形状与请求去向完全不同：

| 维度 | 组合模式 | 职责链模式 |
| --- | --- | --- |
| 结构 | ==树形==（部分-整体层次） | ==链形==（前后相继） |
| 请求去向 | 从父节点广播到==所有后代==，全员处理 | 沿链逐个传递，==被某个节点处理即停== |
| 节点职责 | 处理自己 + 转发给全部子项 | 处理或传给下一个（二选一） |
| 解决的问题 | ==结构复用==：统一对待叶子与容器 | ==流程传递==：解耦请求发送者与最终处理者 |
| 典型场景 | DOM 树、组件树、菜单树、文件系统 | 中间件、审批流、事件冒泡（近似） |

一句话背下来：==组合是"全体广播"——一声令下整棵树响应；职责链是"击鼓传花"——花停在能处理的人手里。== 职责链模式（含中间件实现）在后续 12-职责链模式 篇详述。
