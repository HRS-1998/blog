# 职责链模式

> 使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。把这些对象连成一条链，沿着链传递请求，直到有一个对象处理它为止。

## 解决什么问题

"一个请求该谁处理"会随业务不断变化的痛点：报销审批，1000 以下主管批、一万以下经理批、再往上总监批。最直觉的写法是在发起方堆 if-else——发起者必须认识所有审批者、知道每个的额度，==新增一个"大区总"层级或调整额度，改的是发起方代码==；请求方和处理方深度耦合，谁也没法独立变化。

职责链的解法：==把"处理者"串成链，请求沿链流动，每个节点要么自己处理掉、要么交给下一个节点。== 发起方只认识链头，不关心最终谁处理——链的组成、顺序、增删全部内聚在链本身。新加审批层级只需在链上插一个节点，发起方零改动。

工程价值在两个方向都能用：垂直传递（审批流：谁能处理谁处理，处理完就停）和洋葱包裹（中间件：进的时候层层加工，出的时候层层再加工）。==axios 拦截器、Redux 中间件、Koa/Express、DOM 事件冒泡，全是职责链。==

## 结构说明

- **Handler（处理者）**：定义统一的处理接口；内部持有 `successor`（下一节点）的引用。处理逻辑分两半：==判断自己能不能处理——能则处理并（通常）终止传递；不能则显式转给 `successor.handle()`。==
- **ConcreteHandler（具体处理者）**：实现各自的判断条件与处理逻辑，只关心"我的条件"和"下一棒"，不知道全链长什么样。
- **Client（发起方）**：只把请求交给链头，不感知链的长度与顺序。

两种链形态要分清（面试常混）：

- **纯传递链**：节点要么处理请求要么传给下一个，处理即终止（审批流、事件冒泡的目标查找）。
- **洋葱链（中间件）**：每个节点都会"处理"，`next()` 前的代码在进入时执行、`next()` 后的代码在返回时执行，==一去一回像穿过洋葱==（axios、Koa、Redux 都是这种）。

## 原生 JS 实现

### 1. 经典链式：审批流（setSuccessor）

```js
// 处理者：持有下一节点的引用
class Approver {
  constructor(name, limit) {
    this.name = name;
    this.limit = limit;     // 自己的审批额度（判断条件）
    this.successor = null;  // 下一棒
  }
  // 返回下一个节点，支持 a.setSuccessor(b).setSuccessor(c) 链式设置
  setSuccessor(successor) {
    this.successor = successor;
    return successor;
  }
  handle(amount) {
    if (amount <= this.limit) {
      console.log(`${this.name} 批准了 ${amount} 元的报销`);
      return true;
    }
    if (this.successor) {
      return this.successor.handle(amount); // 条件不够，传给下一棒
    }
    console.log(`${amount} 元无人能批，驳回`);
    return false; // 链尾兜底：整个链都处理不了
  }
}

const lead = new Approver('主管', 1000);
const manager = new Approver('经理', 10000);
const director = new Approver('总监', 100000);

// 链式设置：主管 → 经理 → 总监
lead.setSuccessor(manager).setSuccessor(director);

// 发起方只认识链头
lead.handle(500);    // 主管 批准了 500 元的报销
lead.handle(5000);   // 经理 批准了 5000 元的报销
lead.handle(50000);  // 总监 批准了 50000 元的报销
lead.handle(500000); // 500000 元无人能批，驳回
```

新增"大区总"（额度 50 万）只要 `director.setSuccessor(regionHead)` 一行，发起方与三个老节点零改动——==这就是对修改关闭、对扩展开放。==

### 2. 函数式：数组 + reduce 串链（洋葱模型）

现代 JS 里更常见的是用高阶函数数组描述链，`reduceRight` 把它们叠成嵌套调用：

```js
// 把 [f1, f2, f3] 叠成 f1(input, next=f2(input, next=f3(input, next=tail)))
const pipeline = (...nodes) =>
  nodes.reduceRight(
    (next, node) => (input) => node(input, next),
    (input) => {
      // 链尾兜底：所有节点都调了 next 才会到这里
      throw new Error(`无人处理: ${input}`);
    }
  );

const approval = pipeline(
  (amount, next) => (amount <= 1000 ? `主管批准 ${amount}` : next(amount)),
  (amount, next) => (amount <= 10000 ? `经理批准 ${amount}` : next(amount)),
  (amount) => (amount <= 100000 ? `总监批准 ${amount}` : `驳回 ${amount}`)
);

console.log(approval(500));    // 主管批准 500
console.log(approval(50000));  // 总监批准 50000
console.log(approval(500000)); // 驳回 500000
```

执行轨迹（`approval(50000)`）：f1 条件不满足调 `next` → f2 不满足调 `next` → f3 命中返回——请求沿链流到第三个节点才被处理。这种 `(input, next)` 签名就是 Koa/Redux 中间件的原型。

### 3. AOP 式：Function.prototype.after

不改函数内部，动态把两个函数串成链（《JavaScript 设计模式与开发实践》经典写法）：

```js
// after：先执行自己，返回 undefined 视为"没处理"，转给 nextFn
Function.prototype.after = function (nextFn) {
  const self = this;
  return function (...args) {
    const result = self.apply(this, args);
    if (result === undefined) return nextFn.apply(this, args);
    return result;
  };
};

const byLead = (amount) => (amount <= 1000 ? `主管批准 ${amount}` : undefined);
const byManager = (amount) => (amount <= 10000 ? `经理批准 ${amount}` : undefined);
const byDirector = (amount) => (amount <= 100000 ? `总监批准 ${amount}` : `驳回 ${amount}`);

const approval = byLead.after(byManager).after(byDirector);

console.log(approval(500));    // 主管批准 500
console.log(approval(5000));   // 经理批准 5000
console.log(approval(500000)); // 驳回 500000
```

注意 `after` 每次返回的是==包装后的新函数，原函数不被污染==，这是 AOP 写法优于直接改原型的点（挂 `Function.prototype` 上仍属演示，工程里建议写成独立高阶函数）。

## 前端中的应用

### 1. axios 拦截器链（必考）

`axios.request(config)` 从来不是"直接发请求"，而是把配置穿过一条洋葱链：

```text
请求方向 ──────────────────────────────────────►

  request interceptors        dispatchRequest        response interceptors
  (后注册的先执行)             (真正发 HTTP 的核心)    (先注册的先执行)
 ┌────────────────┐         ┌───────────────┐        ┌────────────────┐
 │ rq2: 加 token   │ ──────► │ 转换数据/发请求 │ ──────► │ rs1: 统一弹错  │
 │ rq1: 改 baseURL │         │ /解析响应      │        │ rs2: 解包 code │
 └────────────────┘         └───────────────┘        └────────────────┘

◄────────────────────────── 响应方向 ──────────────────────────────────
```

源码骨架（`lib/core/Axios.js` + `lib/core/dispatchRequest.js`）就是上面手写的 pipeline：

```js
// 简化版：拦截器数组 + promise 链，链头是 chain 里的 dispatchRequest
Axios.prototype.request = function (config) {
  const chain = [dispatchRequest, undefined]; // [fulfilled, rejected] 成对
  this.interceptors.request.forEach((i) => chain.unshift(i.fulfilled, i.rejected));
  this.interceptors.response.forEach((i) => chain.push(i.fulfilled, i.rejected));
  // request 拦截器 unshift 到队头（后注册的离调用方更近），
  // response 拦截器 push 到队尾——于是形成 [rq2, rq1, dispatch, rs1, rs2]
  let promise = Promise.resolve(config);
  while (chain.length) {
    promise = promise.then(chain.shift(), chain.shift());
  }
  return promise;
};
```

==请求拦截器 unshift 所以后注册先执行；响应拦截器 push 所以先注册先执行==——这两个顺序题是 axios 的高频考点，答案全在这两行 unshift/push 里。

### 2. Redux 中间件：applyMiddleware 与 next(action)

Redux 的 `dispatch` 不是直接到 reducer，而是穿过所有中间件。核心实现只有几行（源码 `applyMiddleware`，此处为等价简化）：

```js
// Redux applyMiddleware 核心（语义等价的简化版）
function applyMiddleware(rawStore, ...middlewares) {
  let dispatch; // 先声明：下面 api.dispatch 闭包引用的是这个变量
  const api = {
    getState: rawStore.getState,
    dispatch: (action) => dispatch(action), // 闭包捕获"最终的"dispatch（延迟绑定）
  };
  const chain = middlewares.map((mw) => mw(api)); // 第一遍：喂 { getState, dispatch }
  // reduceRight 从右往左叠：dispatch = m1(m2(...(rawDispatch)))
  dispatch = chain.reduceRight(
    (next, mw) => mw(next),
    (action) => rawStore.dispatch(action) // 链尾：裸 dispatch，直达 reducer
  );
  return { ...rawStore, dispatch };
}
```

中间件的统一签名 `({ getState, dispatch }) => next => action => result`——==next 是链上的下一棒==，不调 `next(action)` 请求就到此为止（中断）。手写两个经典中间件：

```js
// logger：洋葱模型——next 前是"进入"，next 后是"归来"
const logger = ({ getState }) => (next) => (action) => {
  console.log('dispatching:', action.type ?? '[function]');
  const result = next(action); // 交给下一棒（最后一个 next 是裸 dispatch）
  console.log('next state:', getState().count);
  return result;
};

// thunk：拦下函数型 action，处理完直接 return——不调 next，链被中断
const thunk = ({ dispatch, getState }) => (next) => (action) => {
  if (typeof action === 'function') {
    return action(dispatch, getState); // 异步逻辑自己 dispatch，不走 reducer
  }
  return next(action); // 普通对象才放行给下一棒
};
```

最小可运行的 store + 调用顺序验证：

```js
let state = { count: 0 };
const rawStore = {
  getState: () => state,
  dispatch: (action) => {
    if (action.type === 'INCREMENT') state = { count: state.count + 1 };
    return action;
  },
};

const store = applyMiddleware(rawStore, logger, thunk);
// [logger, thunk] 叠成 dispatch = logger(thunk(rawDispatch))：先穿 logger 再穿 thunk

store.dispatch({ type: 'INCREMENT' });
// dispatching: INCREMENT
// next state: 1

store.dispatch((dispatch) =>
  setTimeout(() => dispatch({ type: 'INCREMENT' }), 100)
);
// dispatching: [function]  （函数也先穿过了 logger）
// next state: 0            （thunk 拦下函数直接返回定时器 id，状态未变）
// —— 100ms 后 ——
// dispatching: INCREMENT   （ thunk 内部拿到的 dispatch 是闭包延迟绑定的最终版）
// next state: 1            （ 所以异步 dispatch 重新穿过整条链，再次被 logger 记录）
```

两个考点藏在这里：==① 中间件注册顺序即洋葱层顺序，`[logger, thunk]` 意味着 logger 在外层；== ==② api.dispatch 用闭包延迟绑定最终组合后的 dispatch——thunk 里再 dispatch 会重新穿过全部中间件，这就是异步 action 也能被 logger 捕获的原因。==（redux-thunk 源码就这十行，本质是把"是不是函数"的判断做成职责链上的一环。）

### 3. DOM 事件冒泡：浏览器内置的职责链

点击一个 `<button>`，事件并不是只给 button——浏览器把请求沿 DOM 树向上传递：`button → div → body → document`，==每一层都有机会处理（addEventListener 注册），调 `e.stopPropagation()` 就截断传递==。这就是一条天然的、树状的职责链：

```js
document.querySelector('.card').addEventListener('click', () => {
  console.log('card 捕获/处理');
});
document.body.addEventListener('click', () => {
  console.log('body 兜底处理');
});
// 点 button：两处都会触发——button 没人处理（没注册），"请求"冒泡上传
// e.stopPropagation() = 职责链的"处理完毕，不再传递"
```

事件委托（把子元素的事件统一挂到父级处理）本质是：==利用冒泡这条链，把 N 个监听器收敛成链上一个节点==，与享元的"减少重复"殊途同归。

## 优缺点与对比

**优点**：

- 发起方与处理方解耦：只认识链头，不关心谁处理、怎么处理。
- 符合开闭原则：新增/删除/重排处理节点，不动既有代码。
- 每个节点单一职责，可以独立测试（mock next 即可）。
- 洋葱形态（中间件）给了请求/响应两个切面，横切逻辑（日志、鉴权、重试）优雅落地。

**缺点**：

- ==请求可能走到链尾也没人处理==，必须设计好兜底（默认 handler / 报错），否则静默丢失。
- 链长了调试困难：断点跳来跳去，"这个请求到底被谁处理了"要顺着链捋。
- 纯传递链的性能损耗：多数节点只是路过（每个节点都要被调用一次）。
- 时序陷阱：axios 拦截器注册顺序 vs 执行顺序、Redux 中间件注册顺序，==背错顺序是常见线上事故==。

### 对比：职责链 vs 中介者（都是"去中心化/中心化"的解耦，方向相反）

两者都为"发起方不认识所有处理方"而生，但拓扑完全相反，详见[中介者模式](./06-中介者模式.md)：

| 维度 | 职责链模式 | 中介者模式 |
| --- | --- | --- |
| 拓扑 | ==线性==：A → B → C，单向后传 | ==星型==：所有人 ↔ 中介者，全连接收敛到一点 |
| 中心角色 | 无中心，链头只是入口 | 中介者是核心，懂业务规则 |
| 交互方向 | 一层层传递，可中断（处理即停） | 全部经由中介者转发、裁决 |
| 谁认识谁 | 节点只认识下一棒 | 同事都只认识中介者 |
| 典型场景 | 审批流、拦截器、中间件、事件冒泡 | 聊天室、全局 store、antd Form |

一句话背下来：==职责链是"踢皮球"——一级级往上踢，踢到能处理的人为止；中介者是"找客服"——不管什么问题都找同一个人，由他分派。==

### 对比：职责链 vs 发布订阅

都消除了"发起方认识接收方"，区别在路由方式与确定性：

| 维度 | 职责链模式 | 发布订阅模式 |
| --- | --- | --- |
| 路由 | 沿固定链顺序传递，==最多一个（或一个都不）处理== | 按事件名广播，==所有订阅者都收到== |
| 接收方数量 | 0 或 1（纯传递链） | 0 到 N |
| 是否可中断 | 可以：处理完/stopPropagation 即截断 | 不可：emit 出去就是全量分发 |
| 顺序保证 | 有严格顺序（链的组成顺序即执行顺序） | 通常按订阅顺序，但语义上不强调 |
| 典型场景 | 审批、拦截器、事件冒泡 | EventBus、DOM 事件注册、mitt |

经验法则：==关心"谁能处理这个请求"用职责链；关心"这个变化要通知谁"用发布订阅。==
