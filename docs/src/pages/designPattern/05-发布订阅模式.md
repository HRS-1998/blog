# 发布订阅模式

> 定义对象间的一种一对多依赖关系，当一个对象的状态发生改变时，所有依赖它的对象都会得到通知并自动更新。

## 解决什么问题

跨模块通信的痛点：A 组件（如支付弹窗）完成了支付，B（购物车角标）、C（订单列表）、D（积分浮层）都需要响应。最直觉的写法是 A 直接调用 B/C/D 的更新方法——A 必须认识所有人，加一个响应方就要改一次 A，对象间织成网状耦合。

发布订阅的解法：==引入一个中间"调度中心"（EventBus），发布者只管往中心扔事件，订阅者只管到中心登记，双方互相不认识。== A 不再知道 B/C/D 的存在，新增/删除响应方对 A 零影响——网状依赖被打散成"都只依赖中心"的星形结构。

代价也随之而来：所有连接都藏在调度中心里，==发布者和订阅者的关系变得不可见，滥用会走向另一个极端——谁发了什么、谁收了什么全靠搜字符串排查，这正是 Vue3 移除实例事件 API 的官方理由。==

## 结构说明

- **EventBus / EventEmitter（调度中心）**：核心角色。维护一张"事件名 → 回调列表"的映射表（通常 `Map<string, Function[]>`），对外提供订阅（on）、发布（emit）、取消（off）等 API。
- **Publisher（发布者）**：只做一件事——`bus.emit('event', payload)`，不关心谁在听。
- **Subscriber（订阅者）**：`bus.on('event', handler)` 登记回调，不关心谁在发。

与观察者模式的角色差异（详见文末对比表）：观察者模式里**Subject 自己维护观察者列表并直接 notify**；发布订阅把这份名单挪到了独立的第三方（调度中心），发布者与订阅者彻底解耦，且天然支持跨模块、跨层级通信。

## 原生 JS 实现

完整 EventBus：on / off / once / emit，==once 用"包装函数 + off"实现==（这是手写题的考点）：

```js
class EventBus {
  constructor() {
    // 核心数据结构：事件名 -> 回调数组
    this.events = new Map();
  }

  // 订阅：把回调登记到对应事件名下
  on(event, handler) {
    if (!this.events.has(event)) {
      this.events.set(event, []);
    }
    this.events.get(event).push(handler);
    // 返回解绑函数（现代库标配，比裸 off 好用）
    return () => this.off(event, handler);
  }

  // 发布：取出该事件的所有回调，逐个执行并传参
  emit(event, payload) {
    const handlers = this.events.get(event);
    if (!handlers) return; // 无人订阅，静默返回
    // 拷贝一份再遍历：防止回调里 off/on 修改原数组导致遍历错乱
    [...handlers].forEach((handler) => handler(payload));
  }

  // 取消订阅：从数组中移除指定回调
  off(event, handler) {
    const handlers = this.events.get(event);
    if (!handlers) return;
    const index = handlers.indexOf(handler);
    if (index !== -1) handlers.splice(index, 1);
  }

  // 一次性订阅：触发一次后自动解绑
  once(event, handler) {
    // 包装原回调：先解绑再执行，保证只跑一次
    const wrapped = (payload) => {
      this.off(event, wrapped); // 注意：解绑的是 wrapped 不是原 handler
      handler(payload);
    };
    this.on(event, wrapped);
  }
}
```

使用示例（含预期输出）：

```js
const bus = new EventBus();

// 1. 基本 on/emit
const onPaid = (amount) => console.log(`购物车更新，支付了 ${amount}`);
bus.on('pay-success', onPaid);
bus.emit('pay-success', 99); // 购物车更新，支付了 99

// 2. 多订阅者：所有回调都会执行（一对多）
bus.on('pay-success', () => console.log('积分 +99'));
bus.emit('pay-success', 100);
// 购物车更新，支付了 100
// 积分 +99

// 3. once：只触发一次
bus.once('login', (user) => console.log(`欢迎 ${user}`));
bus.emit('login', 'ct'); // 欢迎 ct
bus.emit('login', 'ct'); // 无输出，已自动解绑

// 4. off：指定回调取消订阅
bus.off('pay-success', onPaid);
bus.emit('pay-success', 200); // 只剩：积分 +99

// 5. emit 一个没人订阅的事件
bus.emit('nobody-care'); // 无输出、不报错
```

细节提醒（面试加分）：

- `off` 传的必须是**同一个函数引用**——`on('e', () => {})` 后接 `off('e', () => {})` 无效，因为两个箭头函数是不同引用。所以实践中要么保存引用，要么用 on 返回的解绑函数。
- `emit` 时遍历的是拷贝数组，避免回调内部订阅/取消订阅时数组变动导致跳项或崩溃。

## 前端中的应用

### 1. Node.js EventEmitter（模式的工业级标准实现）

Node 的流、HTTP server、进程都是基于 `events` 模块：

```js
const EventEmitter = require('node:events');

const server = new EventEmitter();
server.on('request', (req) => console.log('收到请求:', req.url));
server.on('error', (err) => console.error('出错:', err.message));

server.emit('request', { url: '/api/user' }); // 收到请求: /api/user
```

Node 里几乎所有异步事件的底层都是它——==面试问"发布订阅模式在哪用过"，Node 的 EventEmitter 和 DOM 事件是两个最硬的答案。==

### 2. Vue2 $on/$off 已废弃 → Vue3 用 mitt

Vue2 实例自带事件 API（`this.$on/$emit/$off`），实现跨组件通信；Vue3 **移除了**它们。官方原因：事件挂满组件实例后，==父子组件间的数据流变得难以追溯==——组件的状态变化可能来自任何一处 `$emit`，调试时无法顺着模板和 props 理清来源，维护成本高。

社区标准替代品是 mitt（200 字节，API 与手写版几乎一致）：

```js
// eventBus.js —— 模块级单例（配合单例模式食用）
import mitt from 'mitt';
export const emitter = mitt();

// 组件 A：发布
emitter.emit('pay-success', { amount: 99 });

// 组件 B：订阅（onMounted 注册，onUnmounted 清理，防止内存泄漏）
onMounted(() => emitter.on('pay-success', handlePay));
onUnmounted(() => emitter.off('pay-success', handlePay));
```

注意 mitt 本身不提供 once（需用 `on` + 手动 `off` 自行实现），且`onUnmounted` 里必须成对清理——=="订阅了不解绑"是 SPA 内存泄漏三大源头之一==（另两个是定时器和全局监听）。

### 3. DOM addEventListener 的本质

`addEventListener` 就是一套挂在 DOM 节点上的发布订阅：事件类型是"事件名"，`dispatchEvent` 是"发布"，回调队列由浏览器（调度中心）维护：

```js
const btn = document.querySelector('#submit');

// 订阅：可以给同一事件挂多个回调（一对多）
btn.addEventListener('click', () => console.log('埋点上报'));

const handler = () => console.log('提交表单');
btn.addEventListener('click', handler);

// 手动"发布"：程序触发与用户点击效果一致
btn.click();
// 埋点上报
// 提交表单

// 取消订阅：同样要求传原函数引用（匿名函数注册的监听无法移除）
btn.removeEventListener('click', handler);
```

区别于经典模式的一点：DOM 事件发布者是浏览器（用户交互/渲染时机），回调执行时机由事件循环决定，是异步语义；手写 EventBus 的 emit 则是同步逐个执行。

## 优缺点与对比

**优点**：

- 发布者与订阅者完全解耦（时间解耦 + 空间解耦），任意一方可独立修改、替换。
- 一对多广播天然支持，新增订阅者对发布方零侵入。
- 跨模块、跨层级、跨组件通信的首选（store 之外最轻量的方案）。

**缺点**：

- ==消耗订阅者的判断力：连接关系被藏进中心，调试时"这个事件谁在听/谁发的"全靠全局搜索。==
- 订阅不清理 → 内存泄漏；事件满天飞 → 数据流失控（Vue3 移除 $on 的原因）。
- 同步执行所有回调，某个订阅者抛错会中断后续回调（健壮版要在 try/catch 里包）。

### 对比：发布订阅 vs 观察者模式（必考）

两者常被混为一谈，核心区别是==有没有独立的调度中心、发布者与订阅者是否直接耦合==：

| 维度 | 观察者模式 | 发布订阅模式 |
| --- | --- | --- |
| 调度中心 | ==无==，Subject 自己持有观察者列表 | ==有==，独立的 EventBus 居中转发 |
| 耦合度 | Subject 直接持有 Observer 引用，双方有接口层面的认识 | 发布/订阅双方互不感知，只认识中心 |
| 数据流向 | Subject 状态变化 → 逐个 notify 观察者 | Publisher emit → 中心 → 分发给所有订阅者 |
| 同步/异步 | notify 通常是同步调用 | 中心可实现异步分发、事件队列、离线事件 |
| 典型场景 | Vue 响应式（依赖收集后同步 trigger）、RXJS | EventBus、mitt、Node EventEmitter、DOM 事件 |

一句话背下来：==观察者是"老师点名"——老师（Subject）手里有名单，直接通知每个学生；发布订阅是"公众号"——作者和读者互不认识，全靠平台（调度中心）转发。==

实际前端工程中，因为"中心转发"带来的解耦更彻底，我们日常用的几乎都是发布订阅形态；"观察者模式"这个名字更多出现在框架源码语境（Vue 的 dep/watcher 是标准观察者）。
