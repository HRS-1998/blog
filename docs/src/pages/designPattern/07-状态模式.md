# 状态模式

> 允许对象在内部状态改变时改变它的行为，对象看起来像是修改了它的类。

## 解决什么问题

一个对象的行为随内部状态变化而变化时，最直觉的写法是把状态存成字段，在每个方法里 `switch (status)` 分支判断。状态一多（订单：待支付/已支付/已发货/已完成/已取消……），每个行为方法里都要 switch 一遍，==状态流转规则被拆散在项目的各个角落：改一个状态的流转，要把所有 switch 翻个遍，漏掉一处就出脏数据。==

状态模式的解法：==把每个状态封装成独立的类（或对象），同一个方法在不同状态下有不同实现；"切到下一个状态"由状态自己决定，客户端只管调方法，不关心现在是什么状态。== 分支判断消失了，新增状态 = 新增一个状态类，旧状态想拒绝某个操作，方法里不写就是了（终态保护天然成立）。

它和策略模式的代码结构几乎一样，但意图相反：策略的分支互不感知、由客户端挑选；状态的分支互相认识、自动流转——这个对比是面试必考，文末详说。

## 结构说明

- **Context（上下文）**：持有当前状态对象的引用，把客户端请求委托给当前状态处理；提供 `setState` 供状态类切换自己。
- **State（状态接口）**：所有状态类的统一约定——Context 能发什么请求，状态类就实现什么方法。
- **ConcreteState（具体状态）**：实现"处于本状态时"的行为，并在合适的时机调用 `context.setState(下一状态)` 完成流转。==流转规则写在状态内部，这是与策略模式的分水岭。==

## 原生 JS 实现

红绿灯：三个状态类各管各的行为，`handle` 完自动切到下一状态，Context 完全不知道流转规则：

```js
// 三个具体状态：每个类只关心"我在的时候该怎么表现、下一个是谁"
class GreenState {
  handle(context) {
    console.log('绿灯行');
    context.setState(new YellowState()); // 绿 → 黄
  }
}

class YellowState {
  handle(context) {
    console.log('黄灯等一等');
    context.setState(new RedState()); // 黄 → 红
  }
}

class RedState {
  handle(context) {
    console.log('红灯停');
    context.setState(new GreenState()); // 红 → 绿
  }
}

// Context：红绿灯。只持有当前状态，把请求委托出去
class TrafficLight {
  constructor() {
    this.state = new RedState(); // 初始红灯
  }
  setState(state) {
    this.state = state; // 唯一出口：状态类通过它完成流转
  }
  change() {
    this.state.handle(this); // 委托当前状态，传入自己供切换
  }
}

const light = new TrafficLight();
light.change(); // 红灯停（当前红 → 切绿）
light.change(); // 绿灯行（当前绿 → 切黄）
light.change(); // 黄灯等一等（当前黄 → 切红）
light.change(); // 红灯停（循环往复）
```

对照坏味道版本——流转规则全部内联在 switch 里，新增"黄灯闪烁"要改每个 switch，且规则只有读全代码才能确认：

```js
// 坏味道：状态与流转规则拆散在一个函数里，状态越多越失控
let state = 'red';
function changeBad() {
  switch (state) {
    case 'red': console.log('红灯停'); state = 'green'; break;
    case 'green': console.log('绿灯行'); state = 'yellow'; break;
    case 'yellow': console.log('黄灯等一等'); state = 'red'; break;
    // 新增状态？这个函数以及项目里所有按 state 分支的函数都要改一遍
  }
}
```

细节优化（面试加分）：上面每次流转都 `new` 一个状态对象，而状态类本身无状态数据时，==可以配合单例：三个状态各只有一个实例，`context.setState(GreenState.instance)`，减少无谓的对象创建==。

## 前端中的应用

### 1. Promise：pending / fulfilled / rejected 状态机

Promise 是前端最著名的状态机。三条铁律：==初始 pending；pending 只能流转一次（→ fulfilled 或 → rejected）；落定后不可逆==——`resolve` 里那行守卫就是"不可逆"的实现：

```js
class MyPromise {
  constructor(executor) {
    this.state = 'pending'; // 初始状态
    this.value = undefined;
    this.callbacks = []; // pending 期间攒下的 then 回调
    const resolve = (value) => {
      if (this.state !== 'pending') return; // 关键守卫：只允许从 pending 流出一次
      this.state = 'fulfilled';
      this.value = value;
      this.callbacks.forEach((cb) => cb(value));
    };
    executor(resolve, () => {}); // reject 同理，此处省略
  }
  then(onFulfilled) {
    // 状态模式核心：同一调用，不同状态不同行为
    if (this.state === 'fulfilled') {
      onFulfilled(this.value); // 已落定：立即执行
    } else {
      this.callbacks.push(onFulfilled); // pending：先登记，等落定
    }
    return this;
  }
}

const p = new MyPromise((resolve) => {
  setTimeout(() => resolve('ok'), 100); // 100ms 后才落定
});

// 两次 then 都发生在 pending 期间：全部登记
p.then((v) => console.log('1:', v));
p.then((v) => console.log('2:', v));
// 100ms 后依次输出：
// 1: ok
// 2: ok
```

`then` 在 fulfilled 时同步执行、在 pending 时先存后放——=="同一个方法因状态不同而行为不同"正是状态模式的定义==。同时它还叠加了发布订阅（callbacks 就是订阅表）：状态模式管流转，发布订阅管通知，二者常配合出现。

### 2. 订单/审批流：拒绝"一个 status 字段 + 全员 switch"

订单业务的坏味道：`status` 字段满天飞，每个页面、接口、组件都 switch 一遍"这个状态下能干什么"。状态模式重构后，==每个状态自己封装允许的操作与流转目标，非法操作在当前状态里根本不存在==：

```js
// 状态表：每个状态声明自己支持的操作及流转目标
const orderStates = {
  unpaid: {
    pay(order) { order.state = orderStates.paid; console.log('支付成功'); },
    cancel(order) { order.state = orderStates.cancelled; console.log('订单已取消'); },
  },
  paid: {
    ship(order) { order.state = orderStates.shipped; console.log('已发货'); },
    refund(order) { order.state = orderStates.refunding; console.log('退款申请中'); },
  },
  shipped: {
    confirm(order) { order.state = orderStates.completed; console.log('确认收货'); },
  },
  cancelled: {}, // 终态：什么操作都不支持
};

class Order {
  constructor() {
    this.state = orderStates.unpaid; // 初始状态
  }
  handle(action) {
    const fn = this.state[action];
    if (!fn) return console.log(`当前状态不支持「${action}」`);
    fn(this); // 委托给当前状态，流转在状态内部完成
  }
}

const order = new Order();
order.handle('cancel'); // 订单已取消（unpaid → cancelled）
order.handle('pay');    // 当前状态不支持「pay」（终态天然受保护）
```

审批流（草稿 → 待审批 → 通过/驳回）、会员等级、登录流程同理。复杂场景可直接上 xstate 这类状态机库，核心思路一致。

### 3. 组件 loading / success / error 三态渲染

异步请求组件的渲染就是"状态驱动 UI"。反模式是多个布尔值并存（`isLoading`、`isError` 同时为 true 的非法组合防不胜防），正解是单状态字段 + 分发渲染：

```vue
<template>
  <!-- 三态互斥：由状态字段统一驱动，不存在布尔组合的非法态 -->
  <Loading v-if="status === 'loading'" />
  <ErrorView v-else-if="status === 'error'" :msg="error" @retry="fetch" />
  <Article v-else :data="data" />
</template>

<script setup>
import { ref } from 'vue';

const status = ref('loading'); // loading | success | error
const data = ref(null);
const error = ref('');

async function fetch() {
  status.value = 'loading';
  try {
    data.value = await api();
    status.value = 'success'; // loading → success
  } catch (e) {
    error.value = e.message;
    status.value = 'error'; // loading → error
  }
}
</script>
```

Promise 化的请求库（如 VueUse 的 `useFetch`）内部维护的就是这套状态机，`isPending/isFinished` 都是从单一状态派生出来的。

## 优缺点与对比

**优点**：

- 分支判断被拆进各状态类，每个状态的逻辑可独立阅读、独立测试。
- 流转规则集中在状态内部，"下一个状态是谁"一目了然。
- 新增状态 = 新增状态类，旧代码不动，符合开闭原则；终态保护天然成立。

**缺点**：

- 状态类数量膨胀，两三个状态的简单场景用它属于过度设计。
- 状态类之间互相引用（知道彼此），状态多时流转关系网依然复杂。
- Context 与状态双向持有引用，流转散在各个状态方法里，全局视角不如一张状态图直观。

### 对比：状态模式 vs 策略模式（必考，结构与策略模式如出一辙）

结构几乎一样（Context 持引用 + 委托），差别全在意图与流转归属（详见[策略模式](./02-策略模式.md)）：

| 维度 | 策略模式 | 状态模式 |
| --- | --- | --- |
| 意图 | 算法可替换，关注"怎么做" | 状态驱动行为变化，关注"处于哪个阶段" |
| 分支间关系 | ==互不感知、互不引用== | ==互相知道，能决定下一个状态== |
| 谁来切换 | ==客户端主动选择并注入== | ==Context/状态内部自动流转==，客户端不干预 |
| 运行中切换次数 | 一般选一次用到尾 | 随事件不断流转（红绿灯循环） |
| 典型场景 | 奖金计算、校验规则、缓动函数 | 红绿灯、订单状态机、Promise |

一句话背下来：==策略像"点菜"——客人自己挑；状态像"红绿灯"——灯自己按节奏变，路人只管看。== 面试可补一句：把策略模式的策略换成会互相切换的"状态"，代码一行不改，语义就从策略变成了状态——区别在使用意图，不在代码形状。
