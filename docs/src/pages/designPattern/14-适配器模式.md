# 适配器模式

> 将一个类的接口转换成客户希望的另一个接口，使原本接口不兼容而无法一起工作的类可以一起工作——别名"包装器"（Wrapper）。

## 解决什么问题

"两个东西都很好，就是接口对不上"的痛点：组件库里现成的 UserCard 要 `userName`，后端接口吐的是 `user_name`；新写的组件吃 `data[]`，旧 mock 给的是 `list{}`。直觉解法是在组件里到处写 `user_name ?? userName` 的兼容代码——==兼容逻辑渗进业务的每个毛孔，组件与后端数据格式焊死，后端一改名，全线搜替换。==

适配器的解法：==加一个纯转换层，把旧接口的形状"翻译"成新接口要的形状。== 转换逻辑集中在一个函数/类里，双方各自保持原样——组件只认识标准化模型，后端爱怎么改名只影响 adapter 一处。它不增强功能、不控制访问，==只改形状==。

前端工程里"适配器"出现的密度极高：接口数据适配层、axios 的 `transformRequest/transformResponse`、`Array.from`、旧接口兼容垫片——==凡是"这边的数据给那边用之前先转一下"的地方都是它。== 这可能是实战中性价比最高的模式：一个几十行的 adapter 函数，换来 UI 与后端协议的彻底解耦。

## 结构说明

- **Target（目标接口）**：调用方（新系统/组件）期望的形状——约定的字段名、参数格式、返回结构。
- **Adaptee（被适配者）**：已存在的旧接口——后端遗留接口、第三方 SDK、旧数据格式。它没问题、也不该改，只是形状对不上。
- **Adapter（适配器）**：核心角色。持有/接收 Adaptee 的输出，==做纯粹的"形状转换"==：字段改名、结构重排、单位换算、默认值兜底。对外暴露 Target 形状。

与装饰者/代理的结构区分（三者都是"包一层"）：

- 适配器 ==改形状==（转换前后接口**不同**）；
- 装饰者 ==加功能==（接口相同、行为增强）；
- 代理 ==控访问==（接口相同、行为等价、调用方无感知）。

## 原生 JS 实现

### 新旧接口适配：字段命名转换

旧接口返回 `user_name/age`（下划线），新组件要 `userName`（驼峰）：

```js
// Adaptee：旧接口——能跑、不能改（后端爷爷辈代码，动一下全公司遭殃）
function getUserData(id) {
  // 模拟旧接口返回：下划线命名 + 嵌套
  return {
    user_name: 'ct',
    age: 18,
    contact: { email: 'ct@example.com' },
  };
}

// Target 形状（新组件的约定）：扁平驼峰 + 更明确的字段
// Adapter：唯一知道"旧格式长啥样"的地方
function userAdapter(raw) {
  if (!raw) return null; // 兜底：接口挂了/空数据，不让组件处理脏格式
  return {
    userName: raw.user_name ?? '',          // 字段改名 + 默认值
    age: raw.age ?? 0,
    email: raw.contact?.email ?? '',        // 结构重排：嵌套拉平
    // 新系统要的派生字段：转换层顺便算好，组件保持傻瓜化
    isAdult: (raw.age ?? 0) >= 18,
  };
}

// 新组件：从头到尾只认识 Target 形状，不知道 user_name 的存在
function UserCard({ userName, email, isAdult }) {
  return `${userName} <${email}>${isAdult ? '（成年）' : '（未成年）'}`;
}

// 使用：旧数据 → adapter 翻译 → 新组件
const raw = getUserData(1);
console.log(UserCard(userAdapter(raw)));
// ct <ct@example.com>（成年）
console.log(userAdapter(null)); // null —— 兜底策略集中管理
```

后端哪天重构接口换成 `{ name, email }`，==只改 userAdapter 一个函数，UserCard 与所有调用点零改动==——这就是适配层存在的意义：把"变化的协议"挡在业务之外。

## 前端中的应用

### 1. 接口数据适配层：后端字段 → 组件 props（Vue computed 做视图适配）

真实项目里"最大的一坨适配"是数据层。规范做法是在 `src/adapters/` 里集中翻译，Vue 里最轻的姿势是 computed：

```vue
<script setup>
import { ref, computed } from 'vue';

// 后端原始数据（下划线 + 嵌套 + 分散）
const rawOrder = ref(null);

// computed 就是视图层的 adapter：raw → 组件模板要的形状
const orderView = computed(() => {
  const o = rawOrder.value ?? {};
  return {
    orderNo: o.order_no ?? '—',
    // 分单位换算：后端存"分"，视图要"元"
    amountYuan: ((o.amount_cent ?? 0) / 100).toFixed(2),
    // 状态码 → 文案：翻译逻辑不散进模板
    statusText: { 0: '待支付', 1: '已支付', 2: '已退款' }[o.status] ?? '未知',
  };
});
</script>

<template>
  <!-- 模板里只有标准化的驼峰字段，永远干净 -->
  <div>订单 {{ orderView.orderNo }}：￥{{ orderView.amountYuan }}（{{ orderView.statusText }}）</div>
</template>
```

==UI 与后端协议解耦==是这一层的核心价值：后端字段改名、单位换算、枚举改码，全部收敛在 adapter 里；组件可以被设计稿驱动独立开发（对着 mock 的标准模型写），后端联调只剩 adapter 的搬运工作。BFF（Backend for Frontend）本质上就是把这一层从前端代码挪到服务端。

### 2. axios 的 transformRequest / transformResponse

axios 官方内置了两个适配器插槽，所有请求/响应都会穿过去：

```js
const instance = axios.create({
  // 请求方向的适配器：组件给驼峰 → 后端要下划线
  transformRequest: [
    (data) => {
      if (!data) return data;
      const snake = {};
      Object.keys(data).forEach((key) => {
        // userName -> user_name
        snake[key.replace(/[A-Z]/g, (c) => '_' + c.toLowerCase())] = data[key];
      });
      return JSON.stringify(snake);
    },
  ],
  // 响应方向的适配器：后端吐下划线 → 组件吃驼峰
  transformResponse: [
    (raw) => {
      const data = JSON.parse(raw);
      const camel = {};
      Object.keys(data).forEach((key) => {
        // user_name -> userName
        camel[key.replace(/_([a-z])/g, (_, c) => c.toUpperCase())] = data[key];
      });
      return camel;
    },
  ],
});

// 业务代码：提交 { userName: 'ct' }，后端收到 {"user_name":"ct"}
// 响应 { user_name } 自动变成 { userName }，组件零处理
```

==axios 本身"适配 XHR"这件事也是适配器模式==：浏览器端 `axios.adapters.getAdapter(['xhr', 'http'])` 默认把 XHR 包装成 Promise 接口，Node 端换成 http 模块——同一个 `axios()` 调用在不同运行时下由不同 adapter 适配，这是 axios 同构的原因（也是 `fetch` 出现前最被称赞的设计）。

### 3. 旧代码兼容：mock 数据适配成真实接口格式

联调最痛的时刻：前端对着文档 A 写完，后端交付的是格式 B。与其全局改代码，不如写一个 mockAdapter 把旧 mock 数据"翻译"成真实接口格式，业务代码一行不动：

```js
// 旧 mock（开发时定的格式）：{ list, total }
const mockData = {
  list: [
    { id: 1, title: '文章一' },
    { id: 2, title: '文章二' },
  ],
  total: 2,
};

// 真实接口的格式：{ code, data: { records, total } } —— 直接拿去用会有 undefined 满天飞
const realResponse = {
  code: 0,
  data: { records: [{ id: 1, title: '文章一' }], total: 1 },
};

// 兼容适配器：把两种格式都归一化成组件认识的标准形状
function articleListAdapter(payload) {
  // 命中真实接口格式
  if (payload?.data?.records) return { list: payload.data.records, total: payload.data.total };
  // 命中旧 mock 格式
  if (payload?.list) return { list: payload.list, total: payload.total };
  return { list: [], total: 0 }; // 双兜底
}

console.log(articleListAdapter(mockData));   // { list: [ { id: 1, ... }, { id: 2, ... } ], total: 2 }
console.log(articleListAdapter(realResponse)); // { list: [ { id: 1, title: '文章一' } ], total: 1 }
```

过渡期结束删掉 mock 分支即可——适配器是少数"==注定要删=="的代码，所以更要集中、要薄，绝不掺业务判断。同理还有：第三方地图 SDK 之间互转（项目从高德迁百度，包一个 `MapAdapter`，调用代码不变）、老插件 API 的 shim/垫片（`polyfill` 的一半血统也是适配器）。

## 优缺点与对比

**优点**：

- 解耦：调用方与旧接口互不感知，协议变化收敛在 adapter 一处。
- 复用：让"接口不兼容但功能现成"的东西直接接入（旧接口、第三方 SDK、遗留数据），避免重写。
- 过渡利器：渐进式迁移（mock→真实、旧版→新版）期间的标准化胶水。
- 转换逻辑集中、单一职责、可单测（适配函数是纯函数，测试成本极低）。

**缺点**：

- 多一层转换，==每一次调用都付"翻译税"==（CPU + 心智），数据量大时值得权衡。
- 适配器太多说明系统边界混乱——==它是"对不上"的止痛药，不是治病的药==，长期方案是推动接口标准化。
- 一对多适配容易长歪：一个 adapter 里 if-else 堆五种格式，变成没人敢动的祖传屎山。

### 对比：适配器 vs 装饰者 vs 代理（三者辨析，必考）

三个都是"包一层"，一张表切干净（装饰者详见[装饰者模式](./13-装饰者模式.md)、代理详见[代理模式](./03-代理模式.md)）：

| 维度 | 适配器模式 | 装饰者模式 | 代理模式 |
| --- | --- | --- | --- |
| 意图 | ==改形状==（接口转换） | ==加功能==（行为增强） | ==控访问==（拦截/延迟/缓存） |
| 转换前后接口 | ==不同== | 相同 | 相同 |
| 调用方感知 | 明知要转换（拿了新形状） | 明知在叠加能力 | ==无感知==，当本体用 |
| 层数 | 一层（转一次就够） | 可多层嵌套 | 通常一层 |
| 生命周期 | 过渡期产物，理想中会消失 | 与本体共存、按需组装 | 先于/伴随本体长期存在 |
| 典型场景 | 数据适配层、transform、SDK 互转 | HOC、防抖、memoize、@装饰器 | Vue3 reactive、懒加载、鉴权 |

判断口诀：==拿到的东西"长得不一样了"是适配器；"还是它但更能干了"是装饰者；"还是它、感觉没变"是代理。==

## 相关模式：外观模式

给复杂子系统一个统一的简化入口，让调用方不用关心内部的协作流程。比如上传文件，内部其实要做压缩、格式校验、分片上传：

```js
// 子系统们：各自独立、接口五花八门
const compressor = {
  // 压缩：返回新文件
  compress(file) {
    console.log(`压缩 ${file.name}（${file.size / 1024}KB -> 100KB）`);
    return { ...file, size: 102400 };
  },
};
const validator = {
  // 校验：返回布尔
  check(file) {
    const ok = /^(png|jpg)$/.test(file.name.split('.').pop());
    console.log(ok ? '格式校验通过' : '格式不支持');
    return ok;
  },
};
const chunkUploader = {
  // 分片上传：Promise 接口
  async upload(file, onProgress) {
    console.log('分片上传中...');
    onProgress(100);
    return `cdn.example.com/${file.name}`;
  },
};

// 外观（Facade）：一个干净的入口，内部编排全部子流程
async function upload(file, onProgress = () => {}) {
  if (!validator.check(file)) throw new Error('文件格式不支持');
  const compressed = compressor.compress(file);
  return chunkUploader.upload(compressed, onProgress);
}

// 调用方：一行搞定，不知道也不需要知道内部有三个模块
upload({ name: 'avatar.png', size: 2048000 }, (p) => console.log(`进度 ${p}%`))
  .then((url) => console.log('上传成功:', url));
// 格式校验通过
// 压缩 avatar.png（2000KB -> 100KB）
// 分片上传中...
// 进度 100%
// 上传成功: cdn.example.com/avatar.png
```

### 适配器 vs 外观（都"包一层对外"，方向不同）

| 维度 | 适配器模式 | 外观模式 |
| --- | --- | --- |
| 做的事 | ==转换接口形状==（改形状） | ==简化调用方式==（藏复杂度） |
| 接口数量 | 1 个旧接口 → 1 个新接口（一对一翻译） | ==N 个子系统 → 1 个统一入口==（多对一收敛） |
| 调用方诉求 | "形状对不上，帮我转一下" | "太复杂了，给我一个按钮" |
| 是否新增能力 | 不加功能只改形状 | 不改各子系统，只做编排 |
| 典型场景 | 数据适配层、SDK 互转 | 统一 upload()、封装 SDK（js-sdk 一个 init 搞定全部） |

一句话背下来：==适配器是"转接头"—— Lightning 口转 3.5mm，孔变了；外观是"一键遥控"——电视、音响、窗帘一个按钮全搞定，复杂度被藏起来了。== 前端最常见的外观：给第三方 SDK 包一层自家 `track()`（内部适配多个平台的打点 API——==外观里嵌适配器，两者经常连用==）。
