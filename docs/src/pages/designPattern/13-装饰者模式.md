# 装饰者模式

> 在不改变原对象的前提下，动态地给其添加职责——一种比继承更灵活的"功能叠加"方式，装饰器与本体接口保持一致、层层包裹。

## 解决什么问题

"给已有功能加料"的痛点：一个表单组件，今天要加 loading 态，明天要加埋点，后天要加权限。直觉解法是继承——`WithLoadingForm extends Form`、`TrackedForm extends Form`……==既要 loading 又要埋点就得再来一个 `TrackedWithLoadingForm`，每种组合一个子类，组合数爆炸。== 继承是静态的：编译期定死、类关系固化，父类一动全树抖动。

装饰者的解法：==不改本体、不靠继承，用"同接口的包装对象"把本体裹起来==。装饰器持有本体引用，调用时先做自己的事再转发（或转发后再加工）。要 loading + 埋点 + 权限？三个装饰器任意叠：`withAuth(withTracking(withLoading(Form)))`——==n 个装饰器自由组合，替代 n 层子类树==。运行时还能按条件决定包不包。

前端里这个模式无处不在，只是换了名字：==高阶函数（防抖/节流/memoize）、React HOC、ES7 装饰器语法、axios 的函数包装，本质全是装饰者。== 面试说"装饰者模式"可能觉得陌生，说 `withLoading(Comp)` 立刻就懂。

## 结构说明

- **Component（抽象组件）**：本体与装饰器共同遵守的接口约定。JS 没有接口，靠"函数签名/props 形状一致"这个约定。
- **ConcreteComponent（具体组件/本体）**：真正干活的对象，==完全不知道自己会被装饰==。
- **Decorator（装饰器）**：实现与本体相同的接口（这是与适配器的关键区别——不转形状）；内部持有本体引用，转发请求前后插入增强逻辑。
- **ConcreteDecorator（具体装饰器）**：一种"料"一个装饰器：日志、计时、缓存、重试……各自单一职责，可任意叠加。

关键理解两条：

- ==接口不变、能力增强==：装饰完的东西对调用方来说"还是那个东西"，只是行为多了；
- 层叠顺序即包裹顺序：`withLog(withTiming(fn))` 中 withLog 在最外层，请求先穿它、最后离开它（洋葱语义，与职责链的中间件形态同构）。

## 原生 JS 实现

### 1. 函数装饰器层层包裹：withLog(withTiming(fn))

```js
// 本体：只关心核心职责（模拟一个异步请求）
async function fetchUser(id) {
  await new Promise((r) => setTimeout(r, 50));
  return { id, name: 'ct' };
}

// 装饰器一：日志——签名与本体一致（同参数、同返回），转发前后加料
// 第二参显式传名字：被包裹的可能是匿名 wrapper（fn.name 为 ''），日志里要打谁得说清楚
function withLog(fn, name = fn.name) {
  return async function (...args) {
    console.log(`[log] 调用 ${name}，参数:`, JSON.stringify(args));
    const result = await fn.apply(this, args);
    console.log(`[log] ${name} 返回:`, JSON.stringify(result));
    return result; // 原样透传返回值，调用方对装饰无感知
  };
}

// 装饰器二：计时
function withTiming(fn) {
  return async function (...args) {
    const start = Date.now();
    const result = await fn.apply(this, args);
    console.log(`[time] ${fn.name} 耗时 ${Date.now() - start}ms`);
    return result;
  };
}

// 层层包裹：后包的在最外层。想要三个能力？再写一个再包一层
// withLog 的 fn 是 withTiming 返回的匿名函数，名字得显式传给它
const enhancedFetch = withLog(withTiming(fetchUser), 'fetchUser');

enhancedFetch(1).then((user) => console.log('业务拿到:', user.name));
// [log] 调用 fetchUser，参数: [1]      ← withLog（外层）先进
// [time] fetchUser 耗时 50ms           ← withTiming 开始计时、本体执行完（≥50ms，因机器而异）
// [log] fetchUser 返回: {"id":1,"name":"ct"}
// 业务拿到: ct
```

执行顺序：外层装饰器先进入、最后离开——==与继承版 `class LoggedTimedFetch extends Fetch` 相比，装饰器可以运行时增减、任意排列组合==。

### 2. AOP 式 before / after 装饰

《JavaScript 设计模式与开发实践》的经典写法：不重写包裹函数，而是声明"在前面/后面插入一段逻辑"：

```js
// before：先跑切面，再跑本体（切面抛错则本体不执行）
const before = (fn, beforeFn) =>
  function (...args) {
    beforeFn.apply(this, args);
    return fn.apply(this, args);
  };

// after：先跑本体，再拿结果跑切面
const after = (fn, afterFn) =>
  function (...args) {
    const result = fn.apply(this, args);
    afterFn.call(this, result);
    return result;
  };

// 本体：只管提交
function submit(data) {
  console.log('提交表单:', data.name);
  return 'success';
}

// 前：参数校验；后：埋点上报。两个增强互不知晓，也都不改 submit
const decorated = after(
  before(submit, (data) => {
    if (!data.name) throw new Error('姓名不能为空');
    console.log('校验通过');
  }),
  (result) => console.log('埋点上报:', result)
);

decorated({ name: 'ct' });
// 校验通过
// 提交表单: ct
// 埋点上报: success

decorated({ name: '' });
// Uncaught Error: 姓名不能为空 —— before 抛错，submit 与埋点都不执行
```

before/after 都返回新函数、不污染原函数——这是给既有函数"无侵入加料"的惯用手段（比如给所有按钮 handler 统一加防重复点击，不用改每个 handler）。

## 前端中的应用

### 1. React HOC：withRouter(Connect(Form)) 的嵌套即装饰

HOC（Higher-Order Component）就是装饰者模式的组件形态：==输入一个组件，返回一个"接口相同（吃同类 props、可当组件渲染）、行为增强"的包装组件。== Redux 的 `connect`、React Router 的 `withRouter`、antd 的 `Form.create` 全是装饰器。手写一个简版 withLoading：

```jsx
// 装饰器：持有 Wrapped 引用，渲染前判断 loading，注入切换开关
function withLoading(Wrapped) {
  return function WithLoading(props) {
    const [loading, setLoading] = React.useState(false);

    async function run(task) {
      setLoading(true);
      try {
        return await task();
      } finally {
        setLoading(false);
      }
    }

    if (loading) return <Spinner />;
    // 透传 props + 注入增强能力：对调用方来说"还是那个表单组件，只是多了 loading"
    return <Wrapped {...props} run={run} />;
  };
}

// 使用：层层包裹 = 层层装饰，顺序可换、可增可减
const EnhancedForm = withRouter(withLoading(Connect(Form)));
// connect 注入 redux 数据，withLoading 注入 loading 态，withRouter 注入路由信息
```

React 官方后来的走向也印证了装饰者的痛点：HOC 层层嵌套会出现"==属性来自哪一层说不清=="（props 透传被隐式覆盖）、"==包出来的组件树套娃=="（DevTools 里 `<WithLoading><Connect><Form>` 三层壳）——所以新代码推荐 Hooks（把"料"做成 `useLoading()` 在组件内部组合），==Hooks 与 HOC 之争本质是"组合增强"的两种姿势之争，两者背后都是装饰者思想。==

### 2. ES7/TS 装饰器语法：把"包裹"提升为语言特性

`@decorator` 就是装饰者的语法糖——在定义时把类/方法/属性交给一个函数加工：

```ts
// 方法装饰器：拿到属性描述符，改掉 writable —— 经典 @readonly 示例
function readonly(
  target: any,
  propertyKey: string,
  descriptor: PropertyDescriptor
) {
  descriptor.writable = false; // 装饰器在"类定义时"同步执行
  return descriptor;
}

class User {
  @readonly
  getName() {
    return 'ct';
  }
}

const u = new User();
u.getName = () => 'hacked';
console.log(u.getName()); // 'ct' —— 赋值无效（严格模式下上一行直接 TypeError）
```

Angular 的 `@Component`、NestJS 的 `@Controller/@Get`、MobX 的 `@observable/@action`、Vue Class Component 的 `@Prop`，全是这套。注意 TS 5.0 起支持的是 TC39 标准装饰器（新签名传 `context` 对象、不可再直接改 descriptor），`experimentalDecorators` 旧装饰器仍广泛存在于存量代码——==面试提一句新旧标准差异是加分项。==

### 3. 高阶函数的本质：防抖/节流/memoize 都是装饰者

```js
// 防抖：包装后的函数签名不变、能力增强（延迟合并触发）——标准装饰者
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// memoize：同参直接返回缓存——也是包装增强
function memoize(fn, keyFn = JSON.stringify) {
  const cache = new Map();
  return function (...args) {
    const key = keyFn(args);
    if (!cache.has(key)) cache.set(key, fn.apply(this, args));
    return cache.get(key);
  };
}

const search = debounce((kw) => console.log('请求:', kw), 300);
search('j'); search('ja'); search('jav'); // 300ms 内只发最后一次 → 请求: jav
```

防抖、节流、缓存、重试、错误捕获、埋点包装……日常写的每个 `wrapXxx(fn)` 都是装饰者。==可以说：前端工程师天天在用装饰者，只是多数人不知道它的名字。==

## 优缺点与对比

**优点**：

- 比继承灵活：装饰器运行时组合、任意叠加，n 个装饰器取代组合爆炸的子类树。
- 单一职责：每个装饰器只做一种增强，可独立开发、独立测试。
- 对本体零侵入：不改原类/原函数，想拆随时拆。
- 符合开闭原则：加新能力 = 写新装饰器，旧代码不动。

**缺点**：

- ==层层包装后调用栈变深，调试困难==（错误堆栈里一串 wrapper，DevTools 里 HOC 套娃）。
- 装饰顺序敏感：`withLog(withTiming(fn))` 与 `withTiming(withLog(fn))` 行为不同（计时含不含日志），组合一多顺序就难管理。
- 接口要保持透传纪律：props/参数/返回值漏转发就是事故（HOC 忘记透传 props 是经典 bug）。
- 装饰器与本体"同构多层"，心智负担高于继承的显式类型树。

### 对比：装饰者 vs 代理（结构双胞胎，意图不同）

代码长得几乎一样（都是包一层转发），区分全在意图与感知，详见[代理模式](./03-代理模式.md)：

| 维度 | 装饰者模式 | 代理模式 |
| --- | --- | --- |
| 意图 | ==增强功能==（加日志/计时/loading） | ==控制访问==（拦截/延迟/缓存/鉴权） |
| 调用方感知 | 明知在叠加能力，按需组装 | ==无感知==，以为自己在用本体 |
| 接口承诺 | 与本体一致，但行为更丰富 | 与本体一致，行为等价（受控） |
| 层数 | 可多层嵌套 | 通常一层 |
| 与本体关系 | 装饰者依赖已有本体"往上加料" | 代理通常先于本体存在，替它"看门" |
| 典型场景 | HOC、防抖、memoize、@装饰器 | Vue3 reactive、图片懒加载、权限拦截 |

记忆锚点：==装饰者是"手机壳"——让你更好用，机还是那台机；代理是"保安"——管你能不能进。== 同一个 wrapper 到底算哪个，看它回答的问题是"还能多点什么功能"（装饰者）还是"你有没有资格调"（代理）。

### 对比：装饰者 vs 继承（组合优于继承的经典论证）

| 维度 | 继承 | 装饰者 |
| --- | --- | --- |
| 增强时机 | 编译期/定义时静态确定 | ==运行时动态组合== |
| 组合成本 | 每种能力组合一个子类，==m 种增强最多 2^m 个类== | m 个装饰器自由叠加，就 m 个类 |
| 耦合方向 | is-a，子类绑死父类实现细节（白盒复用） | has-a，装饰器只依赖接口（==黑盒复用==） |
| 对本体影响 | 父类改动波及全部子类 | 本体零感知零改动 |
| 代价 | 类树清晰直观、类型系统友好 | 包装层多、调试与类型推导吃力 |

这是"==组合优于继承=="原则最标准的落地论证：GoF 原话里继承被称为"白箱复用"（看得见父类细节、强耦合），对象组合/装饰是"黑箱复用"（只见接口）。React 从 Mixin（变相继承）→ HOC（装饰）→ Hooks（组合）的演进，就是把这条原则在框架层面走了三遍。
